#ADR-011 元数据与动态数据层

Markdown 链接

本页由构建脚本镜像自仓库 docs/adr/ADR-011-metadata-dynamic-data.md，请修改源文件，不要改本页。

#1 背景与问题（Context）

Kun 的世界观是「编译期已知、显式注册、AOT 零反射、强类型 EF 模型」，低代码的日常是「运行时按元数据建表、动态列、动态校验、动态事件」。Kun 用 IsAotCandidate 开关把不能 AOT 的模块隔离成「非 AOT 孤岛」，这给了 Qian 合法落点：低代码运行时 = 一组住在非 AOT 孤岛里的 Kun 消费方模块（基线 K §3.1）。具体张力：静态 DbSet<T> 与按（类型 × 租户）键的模型缓存 vs 运行时建表；Mediator 按请求 Type 分发 vs 通用 CRUD；Dapper 静态 DTO vs 动态列；稳定事件 ID vs 运行时定义的事件；编译期 IValidator<T> vs 元数据规则（基线 K §3.1 第 1–5 条）。

参考平台的反例：70 种控件共用一个 947 行 POCO、前后端各维护一份隐式契约；改表 = 删表重建、只允许空表，没有「表单加控件 → 加业务列」的迁移；约 47 处拼 SQL、逗号连接代替 JOIN、租户值字面量拼接；鉴权分散在控制器且依赖客户端传参；发布跨十几张表无事务；代码生成「模板即代码」4000 余行、Razor + Roslyn 运行时编译，生成物与运行时漂移；匿名外链不校验开关、读草稿、无有效期；77 个 JSON 文本列无 Schema（基线 F §6；基线 D §6 第 10 条；基线 P §4.3）。值得借鉴的：草稿 / 线上双表与三态、系统列约定、数据权限方案化、无表模式发布即建表、Filter AST 五处共用（基线 F §3.5、§3.9；基线 P §1.3）。

#2 决策（Decision）

  • D11.1 元数据驱动运行时为主轨。元数据（实体 / 字段 / 视图 / 表单 / 列表 / 流程定义）用普通 EF 聚合存储于 qian.metadata，每类元数据有版本化 JSON Schema（2020-12）+ 语义校验，草稿 / 发布双版本 + 不可变快照，可 diff、可回滚，记录来源与审批人；运行态只读发布快照。
  • D11.2 动态数据平面不走 EF 模型：qian.dynamic-data（IsAotCandidate=false）按 entityCode 读写 JSON 行；统一 Filter AST → SQL 生成（参数化 + 来自编译后模型的标识符白名单 + 查询构建器）；强制注入 tenant_id = @tenant AND is_deleted = false；连接打开时设置 RLS GUC；复用租户上下文、RLS、Outbox；按需批量 Resolver 替代全量缓存与 N+1。
  • D11.3 混合存储模型：每个实体一张物理主表；系统列约定 tenant_id、软删三列、审计四列、version 乐观锁、流程状态列、子表 foreign_id；多值 / 子表字段用原生 JSON（jsonb）列或关联表；主键策略保存后不可改。
  • D11.4 正式的 Schema Migrator：元数据 diff → 迁移计划 → 审核 → 逐租户分批执行（批次、并发上限、重试、人工介入点）→ 记录 schema_change_log；「扩展 → 迁移数据 → 收缩」，CREATE INDEX CONCURRENTLY，不承诺自动回滚（回滚 = 回切修订 + 前向兼容数据）；SchemaPerTenant 下循环所有租户 schema；DB 方言为子插件。
  • D11.5 少量泛型命令（CreateRecord / UpdateRecord / DeleteRecord / QueryRecords）注册一次、内部按元数据分派，Pipeline 行为（校验 / UoW / 审计 / 追踪）照常复用；IMetadataValidator(entityDef, payload) 保留字段级错误，错误码 {aggregate}.{field}.{constraint}；通用信封事件 qian.record.changed.v1 同 scope 发出。
  • D11.6 发布拆成可重放幂等步骤：编译 → 迁移 → 切流 → 挂载，记发布日志；功能状态机 未发布 → 已发布 → 已修改 → 已发布；记录生命周期：新建 = 权限裁剪 → 必填 → 唯一 / 业务主键 → 系统字段 → 主副子表同事务 → created 事件。
  • D11.7 Filter AST 在 S1 定义：{logic, groups[{logic, conditions[{field, op, value|sysVar}]}]}，13 个运算符 × 字段类型矩阵，系统变量目录；数据过滤、高级查询、数据权限、启用规则、流程条件五处共用；与 ORM 无关。
  • D11.8 鉴权在数据引擎唯一入口做「资源 + 动作 + 行级」三段式（见 ADR-006）；外链为服务端签发的能力令牌（功能 + 动作 + 版本 + 过滤 + 有效期），不照搬匿名外链。
  • D11.9 控件注册表与 Field Type Catalog 是单一事实源：每控件一次声明 edit / readonly / cell 三种呈现 + Field Type Provider（类型映射、值转换、查询转换、显示转换）；GET /registry/widgets 一份元数据两用；控件目录是数据不是代码。Field Type Catalog 的版本策略与 specs/yue.md D16 一致：控件包与后端 Field Type Provider 同名同版本发布（控件 type 即字段类型编码，前后端同一 SemVer，CI 校验配对），Catalog 按 type@version 登记并按 SemVer 判定兼容。
  • D11.10 代码生成退化为可选「调用运行时 SDK 的薄壳」，不早于 S2 后期（Q11）；不做参考平台式完整 CRUD 源码生成。
  • D11.11 视图（数据集驱动的纯列表）S2 可选，归入列表引擎的「只读数据源」形态，不单独立项（Q17）。
  • D11.12 脚本能力边界（Q18）：S2 只做声明式规则 + 服务端 before / after Hook + 可序列化表达式 DSL（JSON AST）；前端 QuickJS 沙箱为 S2 可选兜底；自由 JS 按钮不做；不用 eval。
  • D11.13 功能编码（Q20）：「租户.应用.功能」命名空间化稳定编码 + id 重映射表；一个功能只归属一个应用，其他应用通过「跨应用引用」挂菜单。编码「前缀 + YYYYMMDD + 六位序列」，名称应用内唯一、编码全局唯一；复制「.副本 + 五位随机」且默认未发布。
  • D11.14 数据接口 SQL 文本模式（Q32）：开放但作为高级权限——只读数据库账号、超时与行数上限、参数化、审计、发布需租户管理员批准；定义层叫「数据接口」（带读写属性），消费侧叫「数据绑定」；「服务出参」保存后不可改。
  • D11.15 门户与报表（Q29 / Q30）：按阶段路线归 S3；S2 提供「配置路径型」门户（固定模板 + 配置）与报表子集（列表 + 分组汇总 + 导出 XLSX）作为可选；交叉表 / 父子格 / 分栏 S3 再评估是否自研展开引擎；服务端出图只用跨平台库（SkiaSharp）并有失败告警。
  • D11.16 打印与 PDF（Q33）：S2 必做模板、版本、数据绑定、浏览器打印；打印设计器 S2 后期；服务端 HTML → PDF S3 可选。
  • D11.17 横切规则只在内核实现一次：可发布元数据统一 draft / published / archived + 当前生效指针（「启用」归档版 = 把指针指回）；导入导出框架；引用登记与被引用保护；字段敏感度标签（PII / 财务 / 机密）S2 进入元数据。

#3 理由（Rationale）

  • 代码生成双轨导致运行时与模板重复实现、行为漂移，元数据运行时是 Agent 生成应用最安全的形态（基线 P §0 第 6 条、§2.4）。
  • 混合存储兼顾迁移管道复杂度、查询能力与多值字段可索引性，是三个候选中的折中（基线 F §9 Q2）。
  • 不走 EF 模型是因为 EF 的模型缓存与静态 DbSet 无法承载运行时建表；泛型命令让 Mediator 与 Pipeline 行为照常工作（基线 K §3.1 第 1–2 条）。
  • Filter AST 在 S1 定义，是数据权限（ADR-006）、流程条件（ADR-012）在 S2 能直接复用的前提。

#4 备选方案与放弃原因（Alternatives）

  • 每功能一组物理表 + 参考平台式建表：无业务列迁移、改表删表重建。放弃。
  • 统一宽表 / 纯 JSON 列：查询与索引能力弱、数据权限谓词难以下推。放弃。
  • EF 动态模型 / 运行时编译实体：与模型缓存、AOT、多租户缓存键冲突。放弃。
  • 代码生成作为主轨：第二真相源、能力漂移、生成物无法复制一套 CRUD 微服务。放弃。

#5 后果与代价（Consequences）

  • 正面：一份 Schema 前后端共用；元数据可校验、可 diff、可回滚，S4 Agent 修改元数据直接复用门禁；动态表与手写表共享租户隔离与审计。
  • 负面：解释器与 SQL 生成器是 S2 的核心工程量；数千租户逐租户迁移的耗时、半升级态与人工介入是各平台都没有完美方案的难点；表达式 DSL 表达力不足有倒退回 eval 的风险。
  • 配套：面向 NpgsqlTransaction 的 IOutboxWriter；序号服务原子化；元数据 Schema 的 CI 兼容检查；Univer 与 React 同栈的表格设计器选型需排除商业包。

#6 对各阶段的影响

  • S1：Filter AST、系统列约定、Field Type Catalog 契约、控件注册表契约、可发布元数据框架、导入导出框架、数据接口契约、应用与菜单模型。
  • S2：元数据注册表、动态数据引擎、Schema Migrator、泛型命令、信封事件、表单 / 列表设计器与运行时、打印、报表子集与配置路径型门户可选。
  • S3：应用包安装、外链能力令牌、设计型门户、表格报表、三方合并冲突预检、SQL 文本模式对客户开放。
  • S4：AI 建表 / 生成元数据经同一校验门禁；元数据以 MCP resources 只读暴露；元数据操作 API 化并暴露状态机。

#7 待确认事项

  • 是否允许业务库由租户自带连接（决策清单 D11 需拍板项，Q1–Q18 未给默认；见 ADR-004 §7）。
  • 大量租户下迁移性能基线与批次参数需技术验证。
  • 表格设计器选型（Univer 开源核心 vs 自研轻量表格）。
  • 条件运算符矩阵已由 S1-DATA-004 按字段类型定义，唯一规格见 数据契约，机器可读目录与 C# 校验器同源分发（基线 W §9.2 第 14 条）。
