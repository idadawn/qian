## 11.1 体验原则

### 11.1.1 渐进披露

**原则。** 默认只展示当前角色、当前阶段、当前任务需要的信息与操作；高级项、危险项、跨阶段项按需展开，且展开有明确入口。

**在产品里的样子。**

- 控制台与应用共用一个外壳，按「平台控制台 / 应用」上下文切换，不开三个窗口；S1 单一侧栏布局，多布局与偏好抽屉留到 S3。
- 安装向导先给结论（装什么、要哪些权限、数据去哪），依赖树、反向权限明细、迁移计划在二级展开。
- 设计器属性面板按「常用 / 校验 / 联动 / 高级」分组；表达式 DSL 与沙箱脚本只在「高级」出现。
- 清单、Schema、审计原文、trace id 等机器面向的信息对开发者与运营可见，对终端用户不出现。

**反例。** 100 多个配置键扁平堆放在一个页面；每个控件三种呈现各自维护一套属性面板。

### 11.1.2 一套表单 / 表格 / 弹层体验

**原则。** 平台后台 CRUD、低代码运行时、设计器预览、审批表单宿主、未来 Agent 生成的界面，使用同一套表单引擎、表格引擎与弹层 API；用户在任何地方遇到的表单与表格行为一致。

**在产品里的样子。**

- 校验时机、错误提示位置、必填标记、只读态呈现、分页与排序、列设置、批量操作、弹层尺寸与关闭行为在平台内只有一种。
- 控件一次声明 `edit / readonly / cell` 三态；设计器左栏与运行时渲染来自同一份控件注册表。
- 业务组件（组织选择、用户选择、字典选择）只是叶子，嵌入同一套表单引擎。

**反例。** 弹窗 / 表单 / 表格双轨并存；系统表单与低代码表单两套校验逻辑；同一个控件在列表单元格、编辑态、只读态三处硬编码。

### 11.1.3 无端差异的元数据

**原则。** 一份元数据 + `device` 维度覆盖，描述 PC、移动 H5 以及未来 Agent 宿主内嵌视图；端之间只有呈现差异，没有语义差异与第二份配置。

**在产品里的样子。**

- 表单 / 列表 Schema 以 PC 为基线，移动端通过 `device` 覆盖项调整布局与可见性；物料端支持矩阵显式声明不支持项并降级，而不是静默消失。
- S2 只交付 PC 响应式，但 Schema 中 `device` 维度与控件 `devices[]` 从 S1 起存在。
- 同一份元数据日后可作为 Agent 宿主中的内嵌视图渲染，权限与 UI 一致。

**反例。** PC 与移动端各存一份表单配置，改一处漏一处。

### 11.1.4 可解释的拒绝

**原则。** 任何「不能做」都给出结构化原因、命中的规则与下一步建议；对人用自然语言，对 Agent 用结构化错误，两者来自同一个判定结果。

**在产品里的样子。**

- 权限拒绝：显示「缺少权限点 X / 数据范围不含该记录 / 字段只读」与「向租户管理员申请」入口；API 返回带错误码、字段、命中策略的 ProblemDetails。
- 校验失败：错误定位到具体控件或 JSON Pointer，并说明允许的取值范围。
- 审批无法提交：显示兜底链每一档为何为空，而不是「提交失败」。
- 配额与预算超限：说明维度（租户 / 应用 / 主体类型）与恢复方式。
- 前端的按钮灰态与隐藏只是预告；服务端拒绝才是裁决，二者文案一致。

**反例。** 「操作失败，请联系管理员」；接口层恒 true、前端自己判断权限。

### 11.1.5 可预览与可回滚

**原则。** 任何会改变租户可见行为的动作——发布功能、升级应用、启用流程版本、批准 Agent 提案、修改权限——都能先看差异、能 dryRun、能在出问题时回到上一个状态。

**在产品里的样子。**

- 发布向导：diff → 迁移计划 → dryRun → 执行 → 发布日志；任意历史版本可对比与回滚。
- 升级中心：冲突预检报告、升级前快照、计划窗口、失败回滚；新增权限的升级必须人工同意。
- 元数据与流程版本：草稿 / 发布 / 归档三态，运行时只读发布快照。
- Agent 提案：差异审阅视图 + 预览渲染 + 批准 / 驳回；批准后仍可回滚。
- 平台级修订：切回旧 digest 即回切。

**反例。** 保存即生效；改表 = 删表重建；升级覆盖租户定制且无快照。

### 11.1.6 授权与开关分开可见

**原则。** 「有没有买 / 被授予（Entitlement）」与「此刻开没开（Enabled / 特性开关）」在界面上是两个独立状态，用户永远能分辨「不可用」是因为没授权还是被停用。

**在产品里的样子。**

- 租户的应用列表同时展示授权状态（试用 / 正式 / 到期）与启用状态；到期后应用不可用但数据保留，续订即恢复。
- 运营控制台对每个租户 × 插件显示两列开关，分别审计。

### 11.1.7 人在回路只有一个收件箱

**原则。** 所有「需要人处理」的事项——审批待办、长任务失败、Agent 补参与确认、升级同意、反向权限批准——都是 Operation，进入同一个「待处理」收件箱，不按来源分散到不同页面。

**在产品里的样子。**

- 收件箱按类型、紧急度、来源主体（人 / 系统 / Agent）过滤；每项携带结构化输入请求并可直接处理。
- S2 的审批四列表是收件箱的一个视图，不是另一套待办模型。
