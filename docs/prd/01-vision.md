# 1. 愿景与定位

> 状态：草案 v1 · 更新日期：2026-10-06 · 决策引用：ADR-001、ADR-002、ADR-003、ADR-014、ADR-016、ADR-018 · 上级索引：[README](README.md)

## 1.1 一句话定位

> **Qian（乾）是一个以插件思维构建、为 AI Agent 时代准备的多租户低代码 PaaS：内核只保留契约、强制执行点与注册表，平台自身的每一项能力都以插件交付；开发者先用它写出多租户应用，业务搭建者再在其上搭建表单与流程，租户最终在应用市场自助选购，而 Agent 从第一天起就能通过同一套契约发现、调用并生成这些能力。**

把这句话拆开：

| 成分 | 含义 | 真相源 |
|---|---|---|
| 多租户低代码 PaaS | 跑在 K3s 上、以 Apollo 为配置中心的 SaaS 底座；多租户、SSO、鉴权、微服务是硬性要求，不是可选特性 | ADR-004、ADR-005、ADR-006、ADR-007、ADR-017 |
| 基于 Kun | Kun 是「微服务开发框架」，是 Qian 内核的实现依赖，而非平台内核本身；以 NuGet + CalVer 锁版本消费 | ADR-001 |
| 插件思维 | 内核最小集 + 一切皆插件；平台自带的租户、身份、鉴权、存储、文件、配置、网关、模型网关都按同一份清单以 `tier: system` 交付 | ADR-002、ADR-003 |
| 先开发者、后搭建者、再租户 | S1 技术底座 → S2 低代码构建 → S3 面向客户 → S4 AI 原生 Agent 平台 | ADR-018、[ROADMAP](../ROADMAP.md) |
| Agent 原生 | 能力契约机器可读、人与 Agent 共用权限与审计、元数据可校验可回滚；S4 经 MCP 对接外部 Agent 运行时，Qian 不写 Agent loop | ADR-016、§02、§10 |
| 前端 yue | React 组件库与外壳，一套表单/表格/弹层引擎贯穿后台与低代码运行时 | ADR-013、specs/yue.md |

## 1.2 与同类的分化

| 维度 | 传统低代码平台 | Agent 平台 | **Qian** |
|---|---|---|---|
| 首要用户与起点 | 业务人员与 IT 支持；一上来就给设计器 | Agent 开发者；一上来就给编排画布与模型接入 | **先给开发者 SDK/CLI/TCK，再给搭建者设计器，再给租户市场；Agent 契约从 S1 起贯穿** |
| 平台能力的组织方式 | 内置模块，功能按菜单堆叠，系统能力与业务能力两套代码路径 | 工具 / 模型 / 策略等类型化插件 | **内核 + 插件；系统能力也是插件，同一清单、同一生命周期、同一 TCK；一份清单派生路由、权限点、菜单、配置命名空间、OpenAPI、MCP 工具** |
| 多租户 | 事后加租户列，租户解析常有请求头兜底与默认回退 | 多为工作空间级隔离，不承诺数据层隔离 | **租户只来自已校验令牌、fail-closed；共享库 + RLS 双保险；租户级生命周期是一等模型，并提供高隔离与私有化两档** |
| 身份与权限 | 自有账号体系，权限校验分散在控制器，可被客户端参数绕过 | API Key 为主，权限随 Key | **平台唯一 issuer（OpenIddict）；权限点由插件清单声明；单一判定点服务 UI / API / MCP 三入口；权限不进令牌、决策可解释** |
| 元数据 | 隐式契约，前后端各自理解；改表等于删表重建 | 工作流 JSON，校验弱、回滚靠人 | **带 Schema、版本化、可 diff、可回滚的元数据；正式的 Schema Migrator；元数据本身即 Agent 的上下文** |
| 应用分发与升级 | 模板复制为主，升级靠人工重导，导出包丢菜单与权限 | 面向开发者的插件市场 | **应用 = 插件包（bundle）；template / managed 两种分发；包格式、升级冲突处理、权益 API 在 S1 定型** |
| 扩展代码的位置 | 进程内脚本引擎、热插 DLL | 沙箱或外部进程 | **第三方代码永不进共享进程；信任等级决定允许的形态；前端不可信 UI 走沙箱** |
| Agent 的角色 | 事后加一个「AI 助手」入口 | 平台核心 | **能力目录就是 Agent 的发现入口；写操作带 Schema 与副作用等级；Agent 作为一等主体、持委托链；S4 对接外部 Agent 运行时而非自建** |
| 模型接入 | 直连厂商 API，各模块各自配置 | 自带模型抽象层 | **复用模型服务网关（GPUStack + Higress）；平台只做租户、配额、计量，不自写模型代理** |
| 部署与运维 | 单体或多进程单库，配置散落 | 云托管为主，私有化弱 | **K3s + GitOps + Apollo；按 digest 的不可变发布；默认共享、高隔离租户、私有化整套 overlay 三档拓扑** |

## 1.3 为什么现在

1. **行业已把 AI 写进低代码的品类定义。** 调研（`research/notes/d3-web-market.md`）确认：权威分析机构 2026 年新版低代码应用平台象限直接以「AI 增强型」命名，其 2025 年的规划假设认为未来几年大部分企业会经由低代码平台落地 Agent；主流厂商都在做同样三件事——自然语言生成应用元数据、把平台能力以 MCP / CLI / Skills 开放给外部编码 Agent、在市场里上架 Agent 组件。一套 2026 年才开始建的平台若不把这些写进底座，上线即落后。
2. **Agent 协议层刚刚稳定，可以押注。** MCP 已进入中立基金会治理，2026-07-28 版把协议改为无状态、授权对齐 OAuth 2.1 与资源指示器；A2A 1.0 已稳定；官方 C# SDK 与 Higress 均已跟进。以这套标准为目标版本从头设计，比在旧协议上修补便宜得多（`research/notes/d5-web-agent-native.md`）。
3. **「平台托管运行时 + 数据不出平台」成为市场信任标签。** 外部托管的集成框架正在被平台托管形态取代，公有 SaaS 普遍「禁第三方任意代码、允许纯元数据包」。Qian 跑在 K3s 上并以插件包为分发单元，天然适合这一形态。
4. **我们自己的前置条件已经具备。** Kun 已有可生产的核心模块与多租户、Outbox、RLS 等设计；团队已有 K3s / GitOps / Higress / MaaS 基础设施与一套经过验证的 React 工程规范；参考平台的功能全集与反例已完成七个领域的基线梳理（`research/baseline-digest.md`）。缺的是把它们按正确的顺序组装起来。
5. **再晚就要为旧设计买单。** 基线明确列出「S1 起就要做对、否则 S4 返工」的清单（带 Schema 的写命令、统一主体模型、可解释权限、一份契约多处生成、租户只来自令牌、审计含主体链）。这些都是底座层的决定，越早定越便宜。

## 1.4 为什么是插件思维

- **内核小才守得住。** 多租户、身份、鉴权是平台的可信计算基，必须「不可绕过」；把它们做成内核的强制执行点，而把一切可替换的东西推到插件里，内核才能小到可以被完整审计与测试。
- **系统能力也是插件，平台才会吃自己的狗粮。** 租户、身份、鉴权、文件、配置这些官方能力按同一份清单、同一生命周期、同一 TCK 交付，意味着第三方插件遇到的每一个坑官方插件会先踩到；SDK 的质量由平台自己先担保。
- **一份清单派生一切，Agent 才有可读的契约。** 清单（`qian-plugin.yaml`）从代码派生、静态可索引，宿主不执行插件代码就能生成路由、权限点、菜单、配置命名空间、OpenAPI 聚合与 MCP 工具描述。这正是 Agent 就绪所需的「能力契约机器可读」，不是另起一套。
- **信任等级决定形态，才能同时服务 SaaS 与私有化。** 官方 module 进程内编译期并入；第三方只能是 package / function / connector / 受限 ui，永不进共享进程。同一套模型下，共享 SaaS 可以安全开放生态，私有化客户可以装自己的 service。
- **应用市场只是插件机制的延长线。** 应用 = 插件包；S1 末「一切皆包」跑通，S2 低代码应用可打包，S3 才上目录与交易。市场不是另一个子系统，而是同一制品流水线换一个消费者。

反过来说明确不做的事（ADR-002）：运行时热插 DLL、进程共享的服务端脚本引擎、把 sidecar 作为默认依赖、引入许可证受限的开源低代码 / AI 平台代码。

## 1.5 为什么先做开发者底座

- **低代码运行时的每一层都压在底座上。** 动态数据引擎要复用租户上下文、RLS、Outbox；审批引擎要复用组织模型、事件总线、调度、表达式规范；设计器要复用元数据版本化契约。先把这些做成可被代码直接消费的技术组件，S2 的引擎才有地基，否则会像参考平台那样在引擎里重复实现一遍租户与鉴权。
- **开发者是最严格的验收者。** 「开发人员用代码在 Qian 上写出一个多租户应用，登录、鉴权、存储、文件、配置、网关、事件、审计全部由平台提供」是 S1 的退出标准（ADR-018）。能让开发者半天写完一个多租户应用的 SDK，才配承载低代码。
- **底座错误最贵。** Kun 当前在多副本多租户下的关键路径缺口（后台链路丢租户、消息至多一次、Outbox 无锁、网关不强制认证）必须先修并用集成测试实证（ADR-001）；这些问题一旦被低代码应用放大，修复成本是数量级增长。
- **插件机制与 SDK 本身就是第一款产品。** 开发者插件市场（面向开发者的组件与连接器）与 S3 面向租户的应用市场共用同一套包格式与发布流水线，只是消费者和授权模型不同；S1 把包格式做对，后面两步才不返工。
- **Agent 就绪不能靠事后补。** 统一主体模型、可解释权限判定、带 Schema 的写命令、审计含主体链都是底座层约定，在 S1 落地的成本最低，在 S4 补的成本最高。
