## 背景

现在每个 PR 都要把 `pm.py build` 的生成物（`pm/index.html`、`pm/tasks.json`、`pm/STATUS.md`）一起提交。这三个文件汇总了全部任务，所以任何两个改了任务文件的 PR，只要先合入一个，另一个就会在这三个文件上冲突。GitHub 对有冲突的 PR 不触发 pull_request 工作流，CI 也就跑不起来。2026-10-15 约两小时内，main 合入了 #111、#115、#122–#128、#130、#131；开着的 #81、#84、#87、#89、#97 等每次都要重新合入 main、重跑 build 再推送，而冲突从来只在这三个文件上。

用户选定的方案：生成物不再进 git。K3s 看板 Pod 按 main 自行生成，CI 只校验任务文件，并把生成的看板上传为产物。分两个 PR 交付：
1. 先让看板 Pod 自行生成。这时生成物仍在 git 里，看板不受影响。
2. 第一个 PR 合入、看板核验通过后，再把生成物移出 git，同时更新文档与 CI。

## 验收

- [x] `pm.py build --out <目录>` 把三个生成物写到指定目录，不带 `--out` 时仍写到 `pm/`。
- [x] 看板 Pod 增加构建容器：
  - git-sync 每切换到一个新提交，就用该提交的 `scripts/pm.py` 生成看板，并原子替换。
  - nginx 从生成目录提供 `/`、`/tasks.json`、`/STATUS.md`，`/tasks/*` 仍取任务源文件。
  - 首次生成完成前，Pod 不就绪。
- [x] 本机用同版本镜像验证构建容器（非 root、只读根文件系统）与 nginx 配置，`kustomize build` 通过。
- [x] 第一个 PR 合入、ArgoCD 同步后，看板提供的 `tasks.json` 与按 main 生成的结果一致；`bootstrap.sh --check` 核验生成提交与同步提交相同。
- [x] `pm/index.html`、`pm/tasks.json`、`pm/STATUS.md` 移出 git 并写入 `.gitignore`；删除 `check-fresh`，docs-and-pm 改为生成看板并上传为产物。
- [x] AGENTS.md、pm/README.md、README.md、deploy/pm-board/README.md 写明新流程：不再提交生成物、在哪看进度、旧分支合入 main 时怎么处理。
