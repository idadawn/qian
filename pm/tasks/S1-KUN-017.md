## 背景

Kun 数据约定（AddKunDataConventions，Qian 的 `AddQianData` 经 `packages/Qian.Data/QianDataExtensions.cs` 调用）以 TryAdd 把 AnonymousCurrentUser 登记进框架当前主体端口（Kun ICurrentUser）；调用方先登记数据组件时 AddKunSecurity 的 TryAdd 落空，命令管道的框架主体比对对一切能力执行判拒（403 `AUTHZ_DENIED`，不写决策日志），服务主体也一样。已在三处宿主各自绕开：测试宿主（CapabilityCatalogTests 先 AddKunSecurity）、联调栈（DevShellHost 先 AddKunSecurity）、参考应用（CrmCommandApplication 在执行调用方配置前 TryAddScoped JwtCurrentUser，S1-YUE-015）。Kun 文档没有写登记次序约定（R132 ③）。

## 方案

### 现状（2026-10-25 核对：Kun main 2aa8e0e 即 v2026.10.23，Qian `KunVersion` 2026.10.23）

- 占端口的兜底：Kun 有两处以 `TryAddScoped<ICurrentUser>(_ => AnonymousCurrentUser.Instance)` 占住框架当前主体端口：`AddKunDataConventions<TContext>`（Kun.EntityFrameworkCore，给 `AuditFieldsSaveChangesInterceptor` 的构造注入兜底）与 `AddKunAuditing<TContext>`（Kun.Auditing，给 `TransactionalAuditingSaveChangesInterceptor` 兜底；同一方法还以 TryAdd 把 `NullTenantContext` 占进 `ITenantContext`）。Qian 只经 `AddQianData` 走到前者。
- 真实适配器也都用 TryAdd，先登记者生效：Kun 的 `AddKunSecurity`（JwtCurrentUser）、`AddKunIdentityAspNetCore`（KunCurrentUser），Qian 的 `AddQianCapability`（`packages/Qian.Plugin.Sdk/CommandPipeline.cs:39`，桥接到 Qian ICurrentUser）与 `AddQianIdentityClient` / `AddQianIdentityS2s`（`packages/Qian.Identity.Client/IdentityClientHosting.cs:163`）。兜底先到时它们全部落空。
- 判拒点：`CommandTransactionBehavior`（`CommandPipeline.cs:71`）要求框架主体已认证、sub 与主体类型都与 Qian 主体一致，否则 `CommandPolicies.Denied()`（403 `AUTHZ_DENIED`）。这一步在 Kun `PermissionBehavior` 与权限引擎之前，所以不写决策审计。
- 靠兜底才能解析的构造注入：Kun 的上述两个拦截器；Qian 的 `QianSoftDeleteInterceptor`（`AddQianData` 以 `TryAddScoped<QianSoftDeleteInterceptor>()` 构造激活，只装数据组件、没有身份适配器的宿主靠兜底解析）。命令管道的端口总有 `AddQianCapability` 的桥接兜着；Kun `PermissionBehavior` 与 Qian `InitializationPermissionServices` 用 `GetService`，允许为空。
- 三处绕开里真正承重的是 `CrmCommandApplication.cs:41`（R132 复核突变 Y3b 去掉它即 403）：测试宿主 `ConfigureIdentity` 的 `AddQianData<IdentityDbContext>` 先于 `ConfigureCapabilities` 的 AddKunSecurity，全靠它兜住。`CapabilityCatalogTests.cs:345` 与 `tools/Qian.Dev.TenantOps/DevHost.cs:62`（联调栈 `DevShellHost` 经 `DevHost.Business` 装配）的「先 AddKunSecurity」都在它之后执行，对这个端口只是重复保险。

### A. Kun 让真实适配器替换可识别的匿名兜底

- 改动点：Kun.Core 加可识别标记（Kun.Core 不依赖 DI 抽象，只能是 BCL 层面的静态工厂委托或专用类型，属新增公共 API）；数据约定与 `AddKunAuditing<TContext>` 用它登记兜底；`AddKunSecurity`、`AddKunIdentityAspNetCore` 改为「端口为空或是这个兜底就 Replace，否则 TryAdd」。Qian 的两处桥接（`CommandPipeline.cs:39`、`IdentityClientHosting.cs:163`）也要照同一规则改，否则「数据组件 + Qian S2S 适配器、不调 AddKunSecurity」的宿主仍然落空。
- 影响面：没有身份适配器的宿主行为不变（端口里仍是匿名），没有破坏性变更。
- 代价：多一个跨包约定与公共 API，每个适配器都得知道并采用这条规则；module 应用手写的 `TryAddScoped<ICurrentUser, 自定义适配器>()` 照样被兜底抢先，陷阱只对 Kun / Qian 自带的适配器消失。「TryAdd 但替换兜底」的语义不直观，后来者容易漏。要发 Kun 新版再在 Qian 钉版。

### B. Kun 让数据约定不再占这个端口

- 改动点：`AddKunDataConventions<TContext>` 删掉 ICurrentUser 的 TryAdd，`AuditFieldsSaveChangesInterceptor` 改用工厂登记，在上下文创建时以 `GetService<ICurrentUser>() ?? AnonymousCurrentUser.Instance` 解析（此时容器已构建完毕，与登记次序无关）；`AddKunAuditing<TContext>` 对 `TransactionalAuditingSaveChangesInterceptor` 同样处理。不新增公共 API，拦截器的公开构造函数不变。Qian 侧：`QianSoftDeleteInterceptor` 改为同样的可空解析（新旧 Kun 都兼容，可先于钉版合入），钉新 KunVersion 后撤销三处绕开写法。
- 影响面：陷阱对所有适配器一起消失（Kun 的、Qian 的桥接、module 应用手写的 TryAdd 适配器），剩下的只是「多个真实适配器时先登记者生效」这条 .NET 通常约定。数据拦截器语义不变：没有身份适配器时创建 / 修改 / 删除主体写 null。
- 代价：行为变更：只登记数据约定、自己又构造注入 `ICurrentUser` 的宿主（靠兜底顺带解析）升级后首次解析即报无法解析 `ICurrentUser`，是大声失败而不是静默判拒。Kun 文档本就要求后台宿主显式绑定 `AnonymousCurrentUser`，CHANGELOG 记「行为变更」（先例：2026.10.13 的 S1-KUN-014）。要发 Kun 新版再在 Qian 钉版。

### C. Qian SDK 装配期检测，直接启动失败（可与 A / B 叠加作护栏）

- 改动点：`AddQianCapability` 登记一次（TryAddEnumerable）启动检查：宿主启动时在新 scope 里解析 Kun ICurrentUser，是 `AnonymousCurrentUser` 就抛出，错误里写明端口、原因与改法（先登记身份适配器再登记数据组件，或升级到修复后的 Kun）。只改 Qian，不必等 Kun 发版。
- 影响面：把现在「每次执行 403、无决策日志」变成「启动即失败、错误里写明改法」。只认 `AnonymousCurrentUser` 这一种明确无效的状态；只跑开户初始化 hook、本来就没有身份适配器的能力宿主会被误拦（仓库里没有这种宿主）。不经 IHost 启动、直接 BuildServiceProvider 的测试不受影响。
- 代价：单独采用时不解除次序约束，三处绕开写法仍然承重，也不满足「装一个包即可独立使用」。叠加在 B 上时只拦显式绑定匿名或其它库的同类兜底，几十行代码加一条用例。

### 发版与钉版（A / B 共同）

Kun PR 合入后在 main 的 merge commit 上打附注 tag（CalVer，例如 `v2026.10.25`），触发 `release.yml` 推 nuget.org。kun 仓库的 CI 与发布都跑在 qd 自托管单 runner 上，各约 25 分钟，nuget.org 索引另有几分钟延迟。Qian 侧钉版提交（`Directory.Packages.props` 的 `KunVersion`、`website/docs/sdk/kun/with-qian.mdx` 状态表、`docs/CHANGELOG.md`）等新版出现在 nuget.org 后再做；等发布期间用本地打包的 Kun 新版在隔离 NuGet 缓存里预验证 Qian 全量测试。

### 推荐

B + C。B 从根上消除次序陷阱、不加公共 API，符合「装一个包即可独立使用」；C 成本很低，把今后任何残留的匿名端口从静默 403 变成启动即失败。A 的可识别兜底要求每个适配器配合，对 module 应用自写的适配器无效，不推荐。顺带发现：`AddKunAuditing<TContext>` 对 `ITenantContext` 的 `NullTenantContext` 兜底是同一机制（先于安全组件登记时租户端口落成无租户）；Qian 不用 Kun.Auditing，建议在同一 Kun PR 以同样的可空解析一并改，或另立 Kun 任务。
