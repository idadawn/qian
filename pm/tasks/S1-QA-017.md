## 背景

dotnet 工作流的测试步骤每次 9.4–14.3 分钟。以 CI 运行 40034799307（PR #260，4 vCPU runner，测试模块按处理器数 4 路并行）的 TRX 归因，32 个模块里最长的两个都慢在测试结构，不慢在容器本身：

- `Qian.Config.Tests` 394.6 秒、55 条：
  - 四个真实 Apollo 类（`RealApolloTests`、`RealApolloFeatureFlagsTests`、`RealApolloReleaseAuditTests`、`RealApolloPortalProtocolTests`）同挂集合 `real-apollo`，但各自 `IClassFixture`，于是 MySQL + AdminService + ConfigService（Portal 类再加 Portal）顺序起了四次。
  - 首次连拉镜像约 197 秒，后三次 41–62 秒（含上一套的释放）；四条用例本身合计约 37 秒。
- `Qian.Sample.Crm.Tests` 366.5 秒、85 条：
  - `CustomerCommandTests` 是分散在 32 个文件里的一个 partial 类，75 条用例。
  - xUnit 对同一个类的用例一律串行，这 75 条排成 353 秒的直线。每条都起完整宿主：DROP SCHEMA、迁移、`app.StartAsync`。

流水线层的改动（路径过滤、预拉镜像、分片）另由一个会话负责，本任务只改 `tests/`，不碰 `.github/`。

## 验收

- [x] Config：四个真实 Apollo 类改由集合夹具共用一套 Portal 版真实 Apollo 栈（Portal 版是超集），各类去掉自己的 Apollo 类夹具，Postgres 类夹具不变。
  - 集合里只启动一次栈。
  - `RealApolloTests` 会停掉 ConfigService 验证离线缓存，由集合的类排序器排在最后；其余三类不受影响。
  - 计数类断言按各自 appId / namespace 或各自的 Postgres 取数，不数全局。
- [x] CRM：`CustomerCommandTests` 按文件主题拆成若干独立测试类，各自 `IClassFixture<PostgresFixture>`。
  - 共用的 `Start()`、辅助方法与常量留在公共基类。
  - 用例方法名、断言、评估报告输出路径（`QIAN_PRODUCT_FILTER_REPORT`、`QIAN_PROFILE_EQUIVALENCE_REPORT` 等）不变。
  - 并行下不稳的用例放进禁止并行的集合。
- [x] 不削弱任何断言；用例数不变：Config 55 条；Sample.Crm 85 条，同步 main 后与 main 相同的 90 条（#259 / #261 新增 4 条，#267 新增 1 条）。
- [x] 本机单跑两个模块，从 TRX 给出改前改后的壁钟与用例数；再跑一次全量 `dotnet test`，无连带失败。
- [ ] 以 PR 的 CI 运行为准：下载 test-results 的 TRX，两个模块的壁钟各在 150 秒以内，对比表写进 PR 描述。
  - 部分达成（#262 合入后的运行 40051232742）：Config 132.5 秒达标；Sample.Crm 178.9 秒未达标，受分片 b 的 CPU 限制，后续见 S1-QA-019。对比表已写进 PR 描述。
