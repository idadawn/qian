## 背景

S1-DEC-022 的真实开通顺序要求：pending 主档 → 组件开通 → tenant/provisioned（SDK hook 成功并审计 channel=hook）→ 管理员及初始授权。但现有 SDK 的 CommandTransactionBehavior.Capture 要求已认证主体的 TenantId 与当前租户一致，TenancyPlugin 又仅放行 active/trial；平台运营主体的 TenantId 为 null。因此不能直接把平台请求的当前主体带入新租户的业务 hook，也不能提前激活或提前授予 owner 来通过验收。

真实复现见 tests/Qian.Sample.Crm.Tests/TenantProvisioningTests.cs 的「真实开通事件接SDK业务hook时保留拒绝_不伪造租户身份或越过pending策略」：Kestrel 宿主、真实 PostgreSQL/RLS、Authz、Lifecycle、HookBridgePlugin 与 SDK 的客户查询能力，开通在 04:provisioned 以 AUTHZ_DENIED 失败，主档仍 pending、初始角色绑定为零。当前无外部请求的内部续跑首先被身份捕获拒绝；即使有租户身份，pending 仍会被租户策略拒绝。

## 验收

- [x] 产品负责人确定开户 hook 的执行身份、授权来源及 pending 期间允许调用的能力边界
- [x] 裁决回填 S1-TEN-003，测试证明初始化 hook 成功审计且普通业务入口仍拒绝 pending
- [x] 对重放、越租户、非开户调用及非许可能力做负面测试，保持 R91 / R96 的事件与初始授予顺序
