## 背景

S1-TEN-006 / 002 / 004 已交付租户运营 HTTP：`plugins/qian.tenancy/contracts/http-v1.openapi.json` 的 8 个路径、11 个操作，由平台超管经旁路调用。产品负责人想在本机逐个调用这些接口，但目前做不到：

- 运营页面归 S1-TEN-005，要等 yue 第 2 波（YUE-007/008/009）；
- 没有 staging（S1-DEP-002/005），也没有真实登录（S1-IDP-002/003）；
- 这些端点只在集成测试的真实宿主里运行。

本任务在既有设计下，给本机一个不写代码就能手测的环境，是 `qian dev`（S1-RT-013）之前的最小替代。装配照搬集成测试已验收的形状：

- 真实 Kestrel，JwtBearer 只收 RS256；
- 受限 PostgreSQL 角色；
- Authz 专用平台登录与 Audit 平台链；
- 平台超管引导；
- 经 Lifecycle 安装并激活平台组件制品。

本任务不新增产品契约，不改既有设计；它不替代 RT-013 的 `qian dev`，也不替代 DEP-002 的 K3s 部署。

## 验收

- [ ] 一条命令起环境：起 Docker PostgreSQL 16，只绑 127.0.0.1；建受限角色与 schema，跑包内迁移；以本机开发 RS256 密钥引导一个平台超管；启动运营宿主 `TenantOperationsHost`。每次启动重建开发库，结果可重复。
- [ ] 开发密钥与数据库口令只在本机生成，放在 git 忽略的目录，不进仓库。
- [ ] 签发开发令牌的小工具：默认签平台超管令牌（`principal_kind=user`，无 `tenant_id`）；也能签租户主体令牌与非超管令牌，用来演示 403。
- [ ] 手测脚本（curl）按顺序走完：建租户 → 开通步骤 → 激活 → 写设置 / 读配额 → 冻结 / 恢复 → 扫描到期。
  - 覆盖运营契约 8 个路径的全部 11 个操作；
  - 附 401 / 403 / 409 反例；
  - 本机实际跑通一遍，结果记在进度日志。
- [ ] 开通步骤与到期扫描没有产品 HTTP 端点，手测宿主只加两条 `/__dev/` 前缀的开发路由：读开通步骤表；代调度器触发 `qian.tenancy/tenant.scan-expired`。两条路由同样要求平台超管令牌，并经超管旁路审计。README 写明它们不是产品契约。
- [ ] README 写明边界：
  - 这是本机开发环境，不替代 S1-RT-013 的 `qian dev`，也不替代 S1-DEP-002 的 K3s 部署；
  - 令牌不代表真实 Identity 签发或登录（IDP-002/003）；
  - 运营页面归 TEN-005。
- [ ] 手测宿主进 `Qian.slnx`，由 CI 构建；本地门禁通过。
