## 背景

S1-YUE-012 把参考应用的界面做成 MF2 远程模块，外壳经 `bridge.invoke` 调 `qian.sample.crm/customer.list` / `customer.create`。请求经网关 BFF 换 S2S（受众 `qian-platform`，主体 user），到平台表面参考宿主（`samples/Qian.Sample.Crm/PlatformSurfaceHost.cs`）的通用执行入口 `POST /api/capabilities/{plugin}/{name}/invoke`；可见性按该用户判定通过后，能力绑定（`packages/Qian.Plugin.Sdk/CapabilityBindings.cs`）在参考应用的 Mediator 里执行。参考栈里 CRM 参考命令宿主是整棵平台插件树的运行时容器，平台表面宿主借用它的装载器，所以命令管道从 CRM 宿主的 DI 解析当前主体，得到的是 `CrmCurrentUser`：它只读本宿主（受众 `qian.sample.crm`）验签时存下的快照、只认 service / agent，看不到平台表面已验证的用户，命令管道入口判拒，结果是 403 `AUTHZ_DENIED`。R130 ③ 把「真实渲染 + 403 + 降级」认作 S1-YUE-012 的验收口径，用户主体执行转为本任务。

授权与审计本来就支持 user：RBAC 命令 PEP 接受 user / service、拒 agent 与 `act`，判 `requiredScopes`、`requiredPermission` 与身份修订并写决策审计；审计策略按主体种类记 `actor_type`。生产里 `module` 应用随 platform 镜像发布，与平台表面同在一个宿主、解析同一个身份适配器（S1-DEP-009）；「两个宿主共用运行时、各登记一个适配器」只出现在参考栈与集成测试里。

可选方案（A 用户主体直通 / B 平台服务主体代执行 + 操作者审计 / C 归 S2）的改动面、安全含义与对真实流程第 4 步的影响由执行会话写成方案交产品负责人，裁决原文见进度日志。按裁决做 A1：

- 参考应用的身份适配器认可同进程平台表面宿主（受众 `qian-platform`）验证过的主体：user 以本人进入命令管道，命令 PEP 按其角色判权限点与 scope，审计链记 `actor_type = user`；参考应用自己的 REST 受众仍只收机器主体，任何带 `act` 的令牌仍拒。
- 不改 `Qian.Plugin.Sdk`、`Qian.Capabilities`、`Qian.Authz`、`Qian.Audit`、`Qian.Gateway` 与 `contracts/v0`；审计来源通道沿用能力登记的 `api`。
- 只覆盖 `module`（进程内）应用；`service` 形态应用跨工作负载的执行（网关直达应用受众，或 RFC 8693 令牌交换带 `act`）不在本任务。
