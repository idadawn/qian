## 背景

S1-CFG-008（idadawn/qian#102）之后，profile 装配的两端 Schema 验证器（CLI 为 Ajv 8.20，.NET 为 JsonSchema.Net 9.4.0）共用正则翻译规则，诊断也归一为出错实例位置。用 77 组 Schema 与配置做差分时，以下情形两端仍不一致，S1-CFG-008 只把它们写进了 `packages/Qian.Profiles/README.md` 的已知分歧：

1. prefixItems 之后的 items。JsonSchema.Net 9.4.0 的 `ItemsKeyword.Evaluate` 跳过前缀后从 0 起算实例位置（上游缺陷，`["a", 1, 2]` 报 `/0`、`/1`，应为 `/1`、`/2`）；Ajv 对 `items: false` 只在数组上报一条。
2. unevaluatedItems。Ajv 对 `false` 只报数组位置；JsonSchema.Net 逐项报告，且按规范把 contains 匹配的项算作已求值，Ajv 不算。
3. minLength 与 maxLength。JsonSchema.Net 用 `StringInfo.LengthInTextElements` 按文本元素计数（`e` 加组合重音算 1），Ajv 按码点计数（算 2）。
4. multipleOf 的小数。Ajv 用浮点取余，`0.3` 不算 `0.1` 的倍数；.NET 按十进制判断为倍数。
5. 超过 2^53 的整数。Ajv 按双精度比较，const、enum、minimum 等的结论与 .NET 不同。
6. `$schema` 声明 draft-07。Ajv2020 无法编译，CLI 报无法解析；JsonSchema.Net 按 draft-07 验证。
7. contains 或 propertyNames 的子 Schema 经 `$ref` 引用、且 Ajv 没有内联引用时，Ajv 的错误不再带外层关联，CLI 多报逐项位置或对象位置。

两端的归一规则在 `ProfileLoader.Locations` 与 `profiles.ts` 的 `locations`。差分做法：把同一组 Schema 与配置写进 `tck/profiles/base` 的临时副本，同时交给 `loadProfile` 与 `ProfileLoader`，逐项比较诊断。

实施中又用差分脚本与随机生成的 Schema（约 3 万组）发现以下分歧，一并处理：

- Schema 有效性：Ajv 编译时按 2020-12 元 Schema 校验并拒绝空 enum，JsonSchema.Net 不校验；`$id`、`$anchor`、`$dynamicRef`、`$recursiveRef`、`$vocabulary`、`dependencies`、Ajv 自有的 `$async` 与 `nullable` 两端解释不同。
- 数值相等：JsonSchema.Net 的 const、enum、uniqueItems 经 decimal 比较，绝对值超过约 7.9e28 时抛错，极小的值舍入为 0。
- Ajv 的缺陷：uniqueItems 在 items 只声明标量类型时跳过类型不符的项；fast-deep-equal 遇到带 `toString` 键的对象抛错；按 `data[key] !== undefined` 判断属性存在，`constructor` 等继承名称算作已提供；properties 与 patternProperties 略过 `__proto__` 键；oneOf 第二个分支成立后不再求值其余分支；已求值属性与项的统计与规范不同（失败的 allOf、$ref、if 仍计入，anyOf 全部失败时项数丢失），在 anyOf 含 if/then、同级有 patternProperties 时验证抛 TypeError。
- JsonSchema.Net 的缺陷：dependentSchemas 与 patternProperties 按 JSON Pointer 转义后的段查找，键含 `/` 或 `~` 时前者静默跳过、后者求值抛 KeyNotFoundException（未被装配器捕获）。
- `$ref`：指向非 Schema 的值、经 `%2F` 编码的段、末尾带换行（.NET 正则的 `$` 在末尾的换行之前也成立，profile 名的校验同理）、`#/`（Ajv 当作根，JSON Pointer 指向根下的空键名）、元 Schema 校验不到的位置（如根下的未知键，Ajv 对其中的 `minLength: -1`、空 `allOf` 照常编译，JsonSchema.Net 构造失败）、不经属性或数组项的循环，两端结论不同。
- Schema 文件里的重复键、超出双精度范围的数值、残缺代理项：JsonNode 拒绝，JSON.parse 接受。以 UTF-16 或 UTF-32 的 BOM 开头时，.NET 的 File.ReadAllText 按 BOM 解码，CLI 按 UTF-8 严格解码而失败。
- 属性的 `default: null`：.NET 不写入，CLI 写入。

## 验收

- [x] 统一语义：items 位置、文本长度按码点、multipleOf 十进制精确、数值按双精度（.NET 先归一）、const/enum/uniqueItems 按 JS 值相等比较全部项、只认自有属性、contains 与 propertyNames 经 `$ref` 时只报数组或键名、oneOf 多个分支成立时只报自身、属性 `default: null` 照常写入；JsonSchema.Net 的三处缺陷（items 位置、dependentSchemas 与 patternProperties 的键名）由装配器绕过
