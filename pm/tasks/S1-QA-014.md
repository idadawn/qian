## 背景

PR #193 的 CI（run 39652096452，job「构建、门禁与测试」）有一条用例失败：`Qian.Identity.Server.Tests.AccountModelTests.解绑最后一个已验证标识被拒绝并返回结构化ErrorDetail_换绑不改sub_软删除释放唯一性`。异常为 `System.IO.IOException: Failed to bind to address http://127.0.0.1:36169: address already in use`，内层是 `AddressInUseException`，栈在 `AccountsHost.Start` 的 `app.StartAsync`。这条用例与该 PR 的改动无关，单独重跑失败的 job 即可通过。

根因：身份测试宿主的发行方地址里带端口，要在构建宿主前确定。现有做法分三步：

1. 先用 `TcpListener(IPAddress.Loopback, 0)` 向系统要一个空闲端口，随即放掉；
2. 接着建表、挂载组件，耗时以秒计；
3. 最后由 Kestrel 绑定。

两步之间端口可能被占走，来源包括：CI 以 `--max-parallel-test-modules` 并行跑的其他测试进程，以及 Testcontainers 容器的宿主端口映射（同样取自临时端口段）。

同样写法有三处：

- `tests/Qian.Identity.Server.Tests/AccountsHost.cs`（账号模型用例）
- `tests/Shared/IdentityProtocolHost.cs`（协议用例，身份服务测试与 CRM 测试共用）
- `tests/Qian.Sample.Crm.Tests/CustomerCommandTests.Identity.cs`，即 CRM `Start(identity: true)`，S1-AZ-009 的修订接线 IT 也走这里

发行方要在构建前写进 OpenIddict 选项、客户端回调地址与组件配置，所以不能改成先绑定端口 0 再回填。拿着探测端口不放直到绑定，又会让并行的容器端口映射失败。所以采用有界重试：绑定失败就换端口、从头建宿主。

## 验收

- [x] 新增共享工具 `tests/Shared/LoopbackPort.cs`，由身份服务测试与 CRM 测试两个项目链接编译：
  - 取一个空闲回环端口交给启动委托；
  - 只在 Kestrel 绑定失败（`IOException`，内层为 `AddressInUseException`）时换端口从头启动，最多 3 次；每次重试发一条诊断消息；
  - 用尽次数后，原样抛出最后一次的异常；
  - 其他失败不重试。
- [x] 三处宿主改用它：
  - 启动失败时，先释放本次创建的宿主、组件加载器与证书，再抛出；
  - 协议宿主的 `reuseAddress`（沿用已停主节点的地址）端口是给定的，不重试；
  - CRM 宿主只在 `identity: true` 时重试，其余监听端口 0，由 Kestrel 原子分配，本来就没有竞争。
- [x] UT（不需要 Docker）：
  - 第一次绑定前端口被占，换端口后成功，新端口能访问；
  - 每次都被占，第 3 次的 `IOException` 原样抛出；
  - 与端口无关的失败只试 1 次。
- [x] 全量 `dotnet test` 通过；身份服务测试与 CRM 的身份相关用例单独各跑一轮通过
