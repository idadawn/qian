## 背景

S1-QA-014（#194）把三个身份测试宿主改成了 `tests/Shared/LoopbackPort.cs`：Kestrel 绑定时端口已被占，就换端口从头启动。之后 S1-IDP-005（#195）新增的 `Qian.Identity.Client.Tests` 带进了三处同样的「先向系统要空闲端口、放掉、隔几秒再绑定」写法，CI 并行时同样会偶发 `address already in use`：

- `IdentityServerHost.Start`：发行方的端口写进 issuer，构建前就要确定，之后还要建表、挂载组件，再由 Kestrel 绑定。
- `RelyingParty.ReserveAddress`：RP 的地址要先作为回调登记到发行方。RP 等发行方起来才绑定，回调已登记，绑定失败也不能换端口。
- `Downstream.Start`（S2sTests）：地址只用来监听，构建前用不到。

三处的约束不同，修法也不同：

- 发行方与 `AccountsHost` 同构，用 `LoopbackPort.StartAsync`。
- RP 改为一直占住端口：IPv4、IPv6 两个回环地址都占，因为 Kestrel 的 localhost 绑定两个都要。到 `RelyingParty.Start` 绑定前一刻才释放，调用处不变。
- 下游改为监听端口 0，启动后读实际地址，竞争从根上消失。

用户在主会话看了 Blocked 列表后回复「处理掉」，由主会话转交本会话。

## 验收

- [x] `LoopbackPort` 新增 `Reserve()`：
  - 占住一个空闲回环端口，IPv4 与 IPv6 回环同号都占；本机没有 IPv6 回环时只占 IPv4；IPv6 同号已被占就换端口，最多 3 次。
  - 释放返回值即放开端口，可重复释放。
  - `StartAsync` 的行为不变。
- [x] `IdentityServerHost.Start` 改用 `LoopbackPort.StartAsync`；启动失败先释放本次的组件加载器、宿主与证书，再抛出。
- [x] `RelyingParty.ReserveAddress` 占住地址，`RelyingParty.Start` 在 Kestrel 绑定前一刻释放，失败路径同样释放；七处调用不改。
- [x] `Downstream.Start` 监听 `http://127.0.0.1:0`，地址取启动后的 `app.Urls`。
- [x] UT（`LoopbackPortTests`，真实 Kestrel，不需要 Docker）：占住期间绑不上 IPv4，IPv6 回环同号也绑不上；释放后立刻能绑定并访问。
- [x] Release 构建 0 警告；`Qian.Identity.Client.Tests` 全部通过；`LoopbackPortTests` 通过
