## 背景

R126 ①（S1-RT-037，2026-10-23）：平台级生命周期操作（安装、激活、回切、弃用、退役）记平台链，但审计端口的平台链入口 `AppendPlatformAsync` 是独立事务——专用平台登录，RLS 要求 current_user 与 session_user 都是平台角色——Lifecycle 的应用角色在自己的事务里写不进平台链，所以只能在状态变更提交之前追加：追加成功之后、本事务提交完成之前的任何失败都会在平台链多留一条孤儿条目（ADR-009 §3 的崩溃窗口取「宁多不漏」）。ADR-009 把同事务写入定为「业务成功即有审计、业务失败即无审计」的唯一正确语义，平台链现在缺这个入口。`packages/Qian.Lifecycle/README.md` 已知限制写明「补同事务端口要改 Audit 的 RLS 策略与 SECURITY DEFINER 函数，归 Audit 所有者另立任务」，本任务即此。

## 验收

- [ ] Audit 提供平台链的同事务入口（形如 `AppendPlatformEnlistedAsync(producer, record, DbTransaction, ct)`，与租户链的 `AppendEnlistedAsync` 同一约束：调用方的可串行化事务、不提交、冲突由调用方换会话重做）：追加由 SECURITY DEFINER 函数以平台链角色完成，调用方的应用角色只获执行权；RLS 仍拒绝应用角色直接读写平台记录，`AuditPlatformAccess` 的现有保证（平台角色不能更新 / 删除历史、不能读写租户数据、普通角色不能借 SET ROLE 冒充）不变；Audit README「受控平台链」与 ADR-009 写明口径
- [ ] qian.lifecycle 的 `PlatformAudited` 改走同事务入口；`LifecycleAuditTests` 里「状态提交失败时平台链多留一条」改为两者都不留，README 已知限制删去孤儿条目一条，R126 ① 补记
- [ ] 突变：改回提交前追加（孤儿条目重现）、函数不校验调用方角色、应用角色直接 INSERT 平台记录各有失败用例；日志逐条记「改了什么 → 哪个用例哪一行失败」

## 进度日志

- 2026-10-23 claude：创建任务（S1-RT-037 验收复核的非阻断项，R126 ①）
- 2026-10-23 claude：状态 → doing
- 2026-10-23 claude：开工前读完 Audit 两条链的实现：租户链同事务入口 `AppendEnlistedAsync` 经 `AuditTransactionWriter` 调 SECURITY DEFINER 函数 `transaction_tip / transaction_append`（属主 writerRole 是 NOLOGIN、NOINHERIT、无成员关系的受限角色，应用登录只获 EXECUTE，函数内 current_user 是属主、session_user 仍是应用登录，租户分支的 RLS 因此放行）；平台链只有独立事务入口 `AppendPlatformAsync`（`PostgresAuditStore<PlatformAuditDbContext>`，绑定专用平台登录），RLS 平台分支要求 current_user 与 session_user 都是平台角色，所以应用登录的事务里写不进平台行。下面三条建议裁决先问用户，用户在本会话亲口确认后再实现。
- 2026-10-23 claude：建议裁决 ①（范围：`Qian.Audit.Native` 要不要同类入口）：给 `IAuditWriter` 加成员后 `NativeAuditService` 必须实现。推荐 A：本任务不给原生存储做同事务平台入口——`NativeAuditService` 以 NotSupportedException 拒绝并在 Native README 写明；gateway 的原生组合不装 Lifecycle，当前没有调用方。备选 B：同步给 `native_tip / native_append` 加「租户登录 + 空租户 GUC + 函数属主身份」分支（要改 `roles-policies.sql` 的固定 guard 模板、`guard-canonical.sql` 与在线逐字校验，Native 测试整套重跑），本任务范围与工期都要扩。
- 2026-10-23 claude：建议裁决 ②（RLS 放宽到什么程度）：若 SECURITY DEFINER 函数以平台登录为属主，函数内 current_user 是平台角色而 session_user 仍是调用方的应用登录，`AuditPlatformAccess` 现有平台分支「current_user 与 session_user 都须是平台角色」必须放宽为只看 current_user——被（误）授予平台角色成员资格的普通登录就能经 SET ROLE 读写平台记录，现有用例「有角色切换权限也不能冒充平台登录」守的正是这一点。推荐 A：平台登录的分支一字不改；为函数属主另加一个分支 `tenant_id IS NULL AND 租户 GUC 为空 AND current_user = 函数属主 AND session_user <> 平台登录 AND 函数属主没有任何成员关系（策略求值时查 pg_auth_members）`。属主是 NOLOGIN、NOINHERIT、无成员关系的受限角色，非超管无法 SET ROLE 成它，成为它的唯一路径是它拥有的两个固定函数；平台登录与普通登录的既有保证（不能更新 / 删除历史、不能读写租户行、SET ROLE 不能冒充）全部维持。函数自身另校验 session_user 是受限登录（非 superuser / BYPASSRLS）、不是平台登录、无租户 GUC、SERIALIZABLE、正文 tenant_id 为空。属主推荐复用租户链函数的属主（`AuditTransactionAccess.CreateMigrationSql` 的 writerRole，宿主不必再建角色），迁移 SQL 为 `AuditPlatformAccess.CreateMigrationSql(platformRole, writerRole, producerRole)` 新重载，1 参重载保留给只用独立事务入口的宿主；备选 A′：另建专用 NOLOGIN 属主（多一个角色、隔离更细）。备选 B：放宽为 current_user = 平台角色即可（不推荐，理由同上）。
- 2026-10-23 claude：建议裁决 ③（公开接口形状）：推荐 A：`IAuditWriter` 新增 `AppendPlatformEnlistedAsync(IPluginContext producer, AuditRecord record, DbTransaction transaction, CancellationToken)`，命名与 `AppendPlatformAsync` / `AppendEnlistedAsync` 对称，生产方检查沿用 `AuditPlugin.Platform()` 的四条、存在租户上下文时拒绝。备选 B：给 `AppendEnlistedAsync` 加带 producer 的重载。两者都是接口新成员（Abstractions 已随 0.2.0 发包，外部实现者会断；仓内三个实现 `AuditService` / `NativeAuditService` / Config 测试替身同步）。
