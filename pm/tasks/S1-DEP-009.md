## 背景

S1-YUE-012 的裁决 ②（产品负责人 2026-10-24 选推荐项 A）：面向用户主体的平台表面在生产里由 platform profile 的平台宿主提供（qian-platform 镜像），本任务交付这个宿主。

这类表面是能力目录、导航、外壳目录（`MapQianCapabilities`，含 `GET /api/capabilities/shell` 与能力执行入口）与有效权限（`MapQianAuthz`）。网关路由表把 `/api/capabilities/**`、`/api/authz/**` 分簇给它（受众 `qian-platform`），外壳 bootstrap 聚合端点（Qian.Gateway 的 `MapQianShellBootstrap`）的三条下游随之。没有这个宿主时，生产外壳的 bootstrap 只能拿到空目录与空权限。

现状：

- `hosts/` 只有 `Qian.Gateway.Host`，没有平台宿主。
- 联调环境与集成测试用的是参考宿主 `samples/Qian.Sample.Crm/PlatformSurfaceHost.cs`。它只认网关 S2S（完整 issuer / 受众 / 有效期 / 签名校验，只接受 RS256），接受 user / service / agent 主体，主体快照取自令牌，按令牌 `tenant_id` 进租户 scope；平台身份没有租户表面；授权 PEP 按生产模式装配，处理器内判定的端点也比对身份修订下限。
- 平台运营端点（`TenantOperationsHost` 的 `MapQianTenancy`）同样走受众 `qian-platform`。两类表面合进同一个平台宿主还是分开，开工时先定。

用户主体执行应用能力（S1-YUE-015 裁决 ④）：参考栈里平台表面宿主把验证过的主体交给参考应用的身份适配器，经通用执行入口调用的 `module` 应用能力以调用者本人执行。生产里 `module` 应用随 platform 镜像发布、与本宿主同进程，解析同一个身份适配器，本任务补同一条验收。装配时注意：Kun 2026.10.25 起（S1-KUN-017）数据约定与实体审计不再占框架当前主体端口（Kun `ICurrentUser`），数据组件与安全组件的登记先后不影响结果；生产根容器仍须登记真实的身份适配器，能力宿主里这个端口解析为 `AnonymousCurrentUser` 时启动即失败（`Qian.Plugin.Sdk` 的启动检查）。

- 2026-11-11 claude：返工 ① 验收 2 的缺陷：受众改为按路由实际匹配到的端点选，不按路径写法。理由：受众与将要执行的端点同一来源；端点路由不区分大小写、忽略结尾斜杠，改前缀比较只是在模仿路由；反方向上运营前缀下也可能匹配到平台端点（带路由参数的平台端点），按前缀选会把运营受众放进平台端点。做法：租户运营接口与经 AddOperations 挂上的端点放进运营端点组（不加路由前缀，只给组里每个端点加运营受众元数据），默认方案的 ForwardDefaultSelector 读匹配到的端点，组内只认 qian-operations，其余路由端点只认 qian-platform；UseQianPlatform 显式先调 UseRouting。没有匹配到路由端点的请求（404，方法不符时的 405 拒绝端点）不执行任何处理器，按声明的运营前缀不区分大小写地选，网关签运营受众转来的这类请求得到 404 / 405，而不是会被外壳当成会话失效的 401。启动时核对运营端点组与声明的运营前缀一致（组内端点都在前缀下，前缀下端点都在组内，不区分大小写），不一致即拒绝启动；运营前缀不得以斜杠结尾。其它「写法不同、路由到同一端点」的情形用独立的小程序以原始请求行实测过（ASP.NET Core 10）：结尾斜杠由路由忽略（已进用例）；百分号编码的普通字符（%74）与点段（/./、/x/../）由 Kestrel 在路由前解码、规范化，匹配到同一端点；双斜杠（含结尾两个斜杠）、反斜杠、%2F 与 ;参数都匹配不到端点（404，不执行处理器）；方法不符时的 405 拒绝端点是普通 Endpoint 而不是路由端点。按端点判定后这些都不需要另行处理。宿主 README、AGENTS.md 与 CRM、Dev.Shell 两份 README 里「按路径分受众」的表述随之改写
