## 背景

S1-CFG-006（idadawn/qian#89）之后，.NET 装配器 `ProfileLoader.Sensitive` 按以下口径判定敏感配置：

- 固定属性名与动态键都按 OrdinalIgnoreCase 不区分大小写，`additionalProperties` 只在按原样没有匹配时适用；
- 动态键用共享翻译器 `packages/Common/SchemaPattern.cs` 按 ECMA-262 可移植子集匹配，单字符位置折叠成等价类；
- 方言判断不同的键名要求 secretRef，超出子集的模式让装配失败。

CLI 的 `packages/qian-cli/src/profiles.ts` 仍是旧口径：

- 属性名区分大小写；
- 动态键用 `new RegExp(pattern)` 按 JS 方言、区分大小写匹配，接受全部 JS 语法；
- `x-qian-sensitive` 不是布尔值时直接忽略，.NET 则装配失败；
- 规则不是对象时仍继续遍历值。

结果是本地 `qian --dump-config` 通过、CI 门禁与运行时装配拒绝。共享 TCK `tck/profiles/cases.json` 同时约束两端，所以 S1-CFG-006 只能把新用例放在 .NET 专属测试类 `ProfileSensitiveConfigTests` 里。

另有一处两端无法逐例一致：模式能否被 .NET 接受，部分取决于 NonBacktracking 构造时的自动机规模估算（默认上限 10000），JS 没有对应限制。

## 验收

- [x] CLI 新增 `schema-pattern.ts`，与 `SchemaPattern.cs` 逐条对应：同一可移植子集、同一稳定性判定、同一折叠与输出；键名比较按 .NET OrdinalIgnoreCase（含增补平面），不用 JS 的大小写转换
- [x] 翻译器两端都显式检查分组配对、`{n,m}` 的 n ≤ m 与规模上限（展开后的字符与锚点不超过 1000），接受与否不再取决于 .NET 构造时的规模估算；上限处的对抗写法在 .NET 都能构造
- [x] 等价类表与跨语言向量由 .NET 生成并有测试守住（`QIAN_UPDATE_VECTORS=1` 重新生成）；TS 测试逐条比对翻译结果、稳定性与键名相等
- [x] `profiles.ts` 的敏感检查与 `ProfileLoader.Sensitive` 同序同义：诊断文案与指针一致，`x-qian-sensitive` 不是布尔值时装配失败
- [x] `ProfileSensitiveConfigTests` 的用例移入共享 TCK，并补充 CLI 旧口径会判错的用例；TCK 新增 `reason` 断言，两端报告精确一致
- [x] README 同步；`pnpm --filter qian test`、`Qian.Profiles.Tests`、`Qian.Common.Tests` 与其余相关 .NET 测试、报告比较、门禁、`check_docs.py`、`pm.py validate` 通过
