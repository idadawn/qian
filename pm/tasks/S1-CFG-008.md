## 背景

S1-CFG-007（idadawn/qian#97）之后，CLI 与 .NET 的 profile 装配在敏感检查上逐例一致；但配置 Schema 仍由两个验证器分别执行（CLI 为 Ajv，.NET 为 JsonSchema.Net），诊断还有三类分歧：

1. 正则写法与语义。Ajv 按 JS 的 u 标志编译 `pattern` 与 `patternProperties` 的键，JsonSchema.Net 按 .NET 的 ECMAScript 选项编译，接受的写法不同：`(?i)a` 在 CLI 报「profile 或组件内容无法解析。」，在 .NET 由敏感检查报配置键处的「不支持的正则写法」；`\u{41}` 只有 Ajv 接受，`[\w-.]`、`a{,2}`、`]` 只有 .NET 接受。都能编译时，`.` 对 `\r` 与 U+2028/2029、`$` 对末尾换行、`\s` 对非 ASCII 空白、`\w` 对 U+0130、代理对计数的判断也不同，值层 `pattern` 与 `additionalProperties` 的结果随之不同。
2. 键序。JS 对象把整数形式的键排在前面，.NET 保留文档顺序；敏感检查遇到首个违规即失败，所以 `limits: {"b": …, "1": …}` 在 .NET 报 `limits/b`，在 CLI 报 `limits/1`。
3. 逐项错误位置。Ajv 对每个缺失的 required 各报一次，给 anyOf、oneOf、if、contains 额外输出汇总错误，propertyNames 与 unevaluatedProperties 报在对象上；.NET 只取最深的失败节点，节点有失败的子节点时它自身的断言（required、uniqueItems 等）被丢弃。缺少 required 属性同时另一属性类型错误时 .NET 少报一条，诊断顺序也不同。

## 验收

- [x] 两端验证器都改用共享翻译器执行 `pattern` 与 `patternProperties`（含 additionalProperties、unevaluatedProperties、propertyNames 的判定），语义按 ECMA-262 无标志、逐码元：`.` 不匹配四个行终止符，`\s` 为 ECMA-262 空白，`$` 只在末尾成立；翻译器、TS 自动机与跨语言向量同步，稳定键名的判定不变
- [x] 交给验证器之前，两端按同一顺序检查 Schema 各子 Schema 位置上的 `pattern` 与 `patternProperties` 键，超出可移植子集的写法在 Schema 文件的对应指针处失败、文案一致；验证器在其他位置编译到不受支持的写法时两端都按无法解析处理
- [x] 敏感检查按序数顺序遍历配置键、`properties` 与 `patternProperties`，两端报告同一个首个违规
- [x] 验证诊断按同一规则归一为出错实例位置并去重、按序数排序：容器关键字只经由失败的子位置报告，其余失败的关键字（含 anyOf、oneOf、not 与 then/else 的汇总）报自身位置，if 的条件与通过的组合下失败的分支不计，contains 报数组位置，additionalProperties、unevaluatedProperties、propertyNames 报到键名
- [x] 共享 TCK 补充上述用例（含 `reason`），两端测试与报告比较通过；验证器其余语义分歧（如 minLength 计数、prefixItems 之后 items 的位置）写入文档并另建任务 S1-CFG-009
- [x] README 与规格同步；`pnpm --filter qian test`、`Qian.Profiles.Tests`、`Qian.Common.Tests`、审计与配置相关测试、全量测试、门禁、`check_docs.py`、`pm.py validate` 通过
