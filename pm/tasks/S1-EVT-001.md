## 背景

组件 `qian.events`（`Qian.Events.Abstractions` / `ctx.Events` + `Qian.Events`，随 SDK 进每个 .NET profile）：`QianEventEnvelope { version, event_id (uuid v7), subject, type, occurred_at, tenant_id, producer, correlation_id?, causation_id?, actor { kind, id, on_behalf_of? }, trace_parent, payload }` 对齐 iClaw 契约；`[IntegrationEventId]` 稳定 ID 与 payload Schema 导出；`Publish` 只允许命令 handler 同 scope；Outbox 发布器批 100、`FOR UPDATE SKIP LOCKED`、publisher confirm、指数退避；exchange `qian.events`（topic）、quorum 队列 `q.<service>.<subscription>`、广播队列；独立模式 Outbox 用宿主 DbContext。与 `Qian.Runtime` 进程内事件不混用。

S1-DEC-013（2026-10-10）裁决：消费端幂等默认用 Kun 的 Redis `IProcessedMessageStore`，PG `processed_messages` 兜底表是本任务的可选项，不做也可；「集成事件只能在命令 handler 同 scope 发出」的分析器规则上游没做（S1-KUN-002 只有运行时 `IScopedPublisher` 兜底），由本任务第 4 条验收落地。

Kun 2026.10.9 行为变更（S1-KUN-009，2026-10-10）：Outbox 表新增可空列 `NextAttemptAt`（持久化指数退避，`RetryBaseDelay × 2^(AttemptCount-1)` 封顶一分钟），参考应用与独立模式宿主 DbContext 都要先生成并应用迁移（kun 仓库 `samples/*/Infrastructure/Migrations/*_OutboxRetrySchedule.cs` 为样板）；默认 `EfOutboxMessageStore` 以 `FOR UPDATE SKIP LOCKED` 领取批次，自定义非事务存储不再默认无锁，须显式 `UseRedisOutboxLock()` 或仅在单实例测试提供 `NullOutboxLockProvider`；消费者成功后才记幂等并 ack，失败经 quorum 队列退避后进 DLX。

## 验收

- [x] IT：参考应用创建客户后 `outbox_messages` +1，RabbitMQ 收到 1 条
- [x] IT：杀掉发布器副本后另一副本接管，无重复发布（confirm 计数 = Outbox 行数）
- [x] UT：信封通过 iClaw `events-schema.json` 校验；每个 `[IntegrationEventId]` 都能导出 JSON Schema
- [x] UT：在非命令 handler 处 `Publish` 触发分析器错误；`actor.kind` 支持 `agent`
