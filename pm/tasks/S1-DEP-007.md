## 背景

2026-10-13 claude 在 S1-DEC-019 R73 复核时经 `ssh qd` 只读核验发现：qd 上的 `k3s.service` 自 2026-10-11 17:05 UTC（北京时间 10-12 01:05）一次停止再启动之后持续崩溃重启，systemd 计数 1089 次，当天 01 到 06 时 UTC 重启 34 次、12:41 到 12:53 UTC 再重启 5 次。每次退出前 kube-controller-manager 报 `leaderelection lost`，进程以状态 1 退出；etcd 在 qd 本地读取 `/registry/leases` 键耗时 1.1 到 4.7 秒（预期 100ms），日志成片出现 `no leader` / `leader changed` / `apply request took too long`，raft 任期已到 4134。qd 本机 I/O 等待与内存压力正常、etcd 库 75 MB、`/etc/rancher/k3s/config.yaml` 自 2026-07-14 未改，可排除本机磁盘与配置改动。

S1-DEP-001 日志记载 worker01 仅余约 372Mi 内存、worker02 仅余 445m CPU / 498Mi，etcd 三个成员中两个在这类 VM 上，是最可能的根因；qd 同时运行两个 GitHub Actions runner 与一个常驻满占一核的进程，加剧控制面争抢。对外表现即 apiserver 间歇返回 ServiceUnavailable（S1-DEP-001 与 S1-DEC-019 R73 记录的现象）。集群级变更需要 root 与审核，不在 claude 的只读权限内。
