## 背景

S1-RT-022 差分时发现，表面解析器在以下与代理项无关的情形两端诊断仍不同。错误码与指针相同，行号、文案或有效性不同：

1. YAML 未闭合的引号标量、制表符缩进：.NET（YamlDotNet）报标量或缩进开始的行，CLI（yaml 包）报检测到错误的行。例如双引号标量在第 1 行开始、到第 3 行读到文件末尾仍未闭合时，.NET 报第 1 行，CLI 报第 3 行。
2. 多个 YAML 文档：.NET 扫描完成后报「文件语法、大小、嵌套深度或值无效。」，在第 1 行；CLI 在第二个文档开始的行报 YAML 语法错误。CLI 的 parseDocument 不解析第二个文档，其中的 alias 与未成对代理项两端结论也不同。
3. JSON 嵌套深度：Utf8JsonReader 的 MaxDepth 为 64，拒绝第 65 层的空容器；CLI 的遍历只在第 65 层有子元素时才拒绝。两端都拒绝时，.NET 报所在行与「JSON 语法无效。」，CLI 报第 1 行与通用文案。
4. JSON 非有限数值（如 1e400）：行号相同，.NET 报「JSON 语法无效。」，CLI 报「文件语法、大小、嵌套深度或值无效。」。其后还有语法错误时，.NET 读到数值即停，CLI 先报全文的语法错误。
5. YAML 多行双引号标量的续行缩进不足（如续行与所在映射同缩进、上一行以转义的引号结尾）：.NET 报标量开始的行，CLI 报续行。
6. YAML 外层映射与其后的嵌套映射都有重复键时：YamlDotNet 构造节点时先报嵌套映射里的（文中靠后），CLI 按文中顺序先报外层的。
7. 未闭合的流式集合：S1-RT-022 起 .NET 不再抛 InvalidOperationException，按扫描停下的位置报；集合内有多行内容时，与 CLI 的行号不同。

应统一行号约定、深度阈值与检查顺序，并补表面 TCK 场景。差分做法同 S1-RT-022：把同一内容交给 SurfaceValidator.Parse 与 parseSurface，逐项比较有效性、指针、行号与文案。

实施时又确认：

- YamlDotNet 要读完一行（或一个多行普通标量）的记号，才把事件交给解析器，以判断能否作简单键。其间的扫描错误会先抛出，所以 alias 改为整篇没有语法错误后再报。
- 两库对文档边界与指令的处理差异很大：多余的 `...`、只有指令的流、`%YAML 1.1` 还会改变 `yaml` 包的解析规则。改为两端同一套逐行预检，依次查禁用字符、指令行与第二个文档。第二个文档开始的行即报，其中的内容两端都不再检查。指令原本两端都接受，现在拒绝。
- 两库各有偏离规范之处：
  - YamlDotNet 18.1.0 在嵌套块映射里吞掉空键之后的值（ParseBlockMappingKey 跳过 Value 记号，却不转入取值状态）；
  - YamlDotNet 接受 `-` 之后的制表符加 tag，并把 `*x:` 的冒号当作值指示符；
  - YamlDotNet 比规范严，拒绝几种块标量开头的空行与流式映射写法；
  - `yaml` 包接受换行之后的冒号，把转义换行之后的空行少算一个换行。

  这些写法两端统一拒绝；YamlDotNet 比规范严之处，CLI 同样拒绝。
- 文件末尾的块标量：front matter 截取时去掉了最后的换行，两库对末尾块标量的结尾换行处理也不同。两端先补一个换行，到输入末尾才发现的错误因此报在最后一行的下一行。
- `Utf8JsonReader` 读到数值之后的分隔符才交出数值，嵌套值里的输入末尾报语法错误。非有限数值与语法错误的先后按此对齐。
- 标量取值也有分歧，一并对齐：
  - 显式 tag `!!str 1` 与 `! 12`；
  - 十六进制大整数的舍入：.NET 原先截断，JS 就近舍入；
  - .NET 正则的 `$` 在末尾换行之前也成立。
- 深度：YamlDotNet 解析很深的流式嵌套会耗尽调用栈或很慢，`yaml` 包组装时报 RESOURCE_EXHAUSTION。两端都在第 65 层集合处提前停止。
- 仍有的分歧写进 `packages/Qian.Surfaces/README.md` 的已知分歧：
  - 数值的文本表示；
  - 多处错误时的行号；
  - 第 65 层之后同一行的扫描错误；
  - 有错的显式复杂键；
  - 本地 tag 含方括号。
- 两端读取表面文件的解码方式不同（UTF-16/UTF-32 的 BOM），与解析器无关，另建 S1-RT-027。
