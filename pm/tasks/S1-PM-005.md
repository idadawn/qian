## 背景

S1-PM-004 上线后留下两处问题：

- Deployment 用 `Recreate`，先停旧 Pod 再起新 Pod，新 Pod 就绪前看板不可用。#136 上线时新 Pod 调度到 k3s-worker02，git-sync 镜像拉不下来，看板一直不可用，直到 #140 把 Pod 固定到 qd。
- git-sync 在 builder 生成途中切到新提交、删掉旧检出时，builder 会记一条「生成失败」。下一轮会生成新提交，结果正确，但这条日志是误报。

改滚动更新有一个前提：2026-10-16 实测 qd 可分配 CPU 8 核，已请求 7980m，只剩 20m；看板 Pod 请求 30m（三个容器各 10m），新旧 Pod 同时存在时排不上。实测用量是 git-sync 4m、builder 1m、nginx 1m。

## 验收

- [x] Deployment 改为 `RollingUpdate`（`maxSurge: 1`、`maxUnavailable: 0`）：新 Pod 就绪前旧 Pod 继续提供看板；新 Pod 拉不到镜像或排不上时，旧版不受影响。
- [x] 三个容器的 CPU 请求按实测降到 5m（合计 15m），滚动时新旧两个 Pod 能同时放进 qd 的 CPU 余量；清单注释与 README 写明这个前提，以及余量不足时的表现。
- [x] builder 生成途中 git-sync 换了提交（旧检出被删）时不记「生成失败」，改记一条跳过说明，下一轮生成新提交；真正的生成失败照旧记录。本机可重复运行的测试覆盖正常生成、真失败与途中切换三种情形。
- [ ] 合入、ArgoCD 同步后核验：滚动更新期间持续访问看板没有失败请求；`bootstrap.sh --check` 全部通过。
- [ ] 滚动更新收尾干净：旧 Pod 的 nginx 停止前先等转发规则摘掉它；builder 收到 SIGTERM 立即退出，旧 Pod 不必等宽限期；新生成的 builder ConfigMap 带 `IgnoreExtraneous` 注解，清理此前留下的旧 ConfigMap 后 ArgoCD 应用回到 Synced。
