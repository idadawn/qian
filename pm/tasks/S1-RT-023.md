## 背景

另一会话执行 S1-DEC-021 的阻塞任务序列时，本机全量 `dotnet test` 偶发 `Qian.Runtime.Tests` 的 `RuntimeScenarioTests` 失败（T25-replace：trace 第 4 项期望 `dispose:consumer`，实得 `apply:consumer`），单独跑该类 6 次全过。

根因：`PluginLoader.ReconcileCoreAsync` 只在循环开始与每轮末尾经 `CleanPendingAsync` 快照并撤销 Pending 节点的旧上下文，挑选待 Apply 的节点时不检查它是否仍持有旧 `Context`。另一线程（`RegistrationHandle.Replace`、注册 `Dispose`、restriction 变更，例如表面热重载的文件监视线程）若在最后一次快照之后、下一次挑选之前经 `Notify → InvalidateDependents` 把依赖者标成 Pending，依赖者会在旧效果未撤销时重新 Apply：旧效果与旧注册泄漏且永不释放；旧上下文登记过服务时，新 Apply 的 `Provide` 撞同 scope 冲突而 Failed。T25 中挂载留下的异步级联恰好与测试线程的 `Replace` 交错。TS 运行时 `#reconcile` 结构相同：清理在等待某个撤销时，另一调用方让依赖者失效，同样会跳过撤销。

## 验收

- [x] UT：确定性复现。provider 提供 X、Y 并留句柄；consumer 注入 X、登记服务与效果；D 注入 Y，效果撤销时等待 gate。`Replace(Y)` 使清理卡在 D 的撤销上，此时另一线程 `Replace(X)` 使 consumer 失效，再放开 gate。修复前 consumer 未撤销即重新 Apply，修复后先撤销再 Apply，无清理异常、无残留注册（`RegistrationHandleTests.Replace_during_cascade_cleanup_disposes_the_stale_dependent_before_reapply`；修复前连续 6 次失败，第 4 项期望 `dispose:consumer`、实得 `apply:consumer:x2`）
- [x] 修复：两侧装载器挑选待 Apply 节点前，若仍有持旧上下文的 Pending 节点，先逆序撤销再重新挑选，保证「撤销后再 Apply」；不放宽既有断言
- [x] TCK：共用场景覆盖「级联清理期间依赖者被并发失效」，.NET 与 TS harness 读同一 YAML 通过；场景格式新增的操作写入 `tck/runtime/README.md`（`replace-during-cleanup.scenario.yml`；新增 `effect.gate`、`replace` 的 `idle: false` 与 `blocked` / `open` / `idle`；修复前两侧均稳定失败）
- [x] 负载下 T25 不再偶发：修复前后在 CPU 压力下重复运行 T25，给出次数统计（未提交的临时压力测试，36 个并发 worker 反复跑 T25：修复前 7920 次失败 56 次，特征与报告一致；修复后 8640 次零失败）
- [x] 门禁：dotnet 全量构建与测试（带 `QIAN_BUF_PATH` / `QIAN_OASDIFF_PATH`）、`check_deps`、门禁自测、`check_docs`、`pm.py validate` / `build` / `check-fresh`、`pnpm --filter ./packages/qian-runtime test` 通过（本机并入最新 main 后全量 732/732 零跳过；CI 以 [idadawn/qian#112](https://github.com/idadawn/qian/pull/112) 全部检查通过为合并前提）
