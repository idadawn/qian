## 背景

S1-AZ-003 第二轮验收复核（2026-10-16）的结论是四条验收成立，任务置 done。第一轮复核记下的非阻断缺口里，有两处已经落定：

- 「每次判定读一次修订号」的开销，归 S1-AZ-004 评估（R103）。
- Qian.Registry README 的过期句，已在 #153 修正。

剩下三处缺口不在 AZ-003 的验收里，也没有任务承接，收进本任务。第二轮复核还提了几条加固 #153 新用例的建议，一并放在这里。这些都是 AZ-003 已交付、却没有用例证明的路径，坏了不会有测试报警：

- **AuthzPlugin 的判定快照缓存接线**：`AuthzPlugin` 从宿主取 `IKunCache` 传给 `RbacPermissionChecker`（AuthzPlugin.cs 的 Apply）。S1-AZ-003 验收 3 的「≤ 3 秒」用例直接构造 checker、自己传缓存，CRM 等宿主也没注册缓存。经组件装配时，缓存是否真被用上，授予与撤销是否在下一次判定生效，都没有用例。
- **超管旁路在审计写入失败时拒绝**：`SuperadminBypassService` 在审计写入抛错时返回 `audit_failed` 拒绝，这个分支没有用例。审计组件卸载后返回 `audit_unavailable` 的那支已有用例。
- **注册表管理面经 HTTP 的超管路径**：`ScopeSuperadminTests` 在进程内调 `GetScopeViewAsync`；经真实 HTTP 的管理面用例（`ScopeManagementTests`）只覆盖租户主体。S1-TEN-006 只验 tenancy 端点。S1-RT-029 的写入端点将来也会走同一旁路。
- **完整解释用例的断言偏弱**：#153 新增的「经ctx_Authz取完整解释…」有四处可加强：
  - 只验了授权定位的 `grant:` 前缀。
  - owner 只有一个角色，分不出「命中角色」和「全部角色」。现在的引擎口径是：放行与只缺 step-up 时只列带有该授权的角色，无授权拒绝时列主体全部有效角色。
  - 与 CheckAsync 只比了 Allow。
  - 跨租户用例在主体校验阶段就提前返回，没走到 RLS，也没断言 Missing。

## 验收

- [x] IT：经 PluginLoader 装载 AuthzPlugin，宿主注册 `IKunCache`，memory 与 redis 各一行：第二次判定命中缓存，授予、撤销后的下一次判定即反映变化（口径同 S1-AZ-003 验收 3）；宿主未注册缓存时判定照常
- [x] IT：超管旁路在审计写入失败（写入抛错，不是组件卸载）时拒绝，原因 `audit_failed`，不放行，也不留下半条审计；写入恢复后同一请求放行，并记入目标租户审计链
- [x] IT：经真实 HTTP（`Qian.Registry.AspNetCore` 的 scope 视图端点），平台超管读取租户 scope 放行，并在目标租户审计链记 `bypass = superadmin`；非超管平台主体、未配置 `platformRole`、跨租户时与租户主体同口径拒绝，且不写审计
- [x] IT：加固完整解释用例：放行时 MatchedGrants 与库里实际授权行的定位逐一对照；owner 另加一个不含该授权的角色，放行时 MatchedRoles 只含带有该授权的角色、无授权拒绝时为全部有效角色；与 CheckAsync 同时比较 Allow 与 Reason；跨租户改用租户 B 中同 id 的主体，走到 RLS 之后断言 MatchedRoles / MatchedGrants 为空、Missing 只含被拒权限点
