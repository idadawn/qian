## 背景

`AuditInputPolicy` 用 .NET 默认语义（Unicode）匹配 `patternProperties`。紧随其后的 Schema 验证器 JsonSchema.Net 9.4.0 按 `RegexOptions.ECMAScript` 评估同一键名，`\d`、`\w`、`\s` 只认 ASCII。JSON Schema 2020-12 核心规范 §6.4 规定的方言则是带 u 标志的 ECMA-262。三者在否定类、`.`、`$`、非 ASCII 空白与代理项上判断不同。

已复现两个方向的泄漏：

- 敏感模式 `^\W+$` 配非敏感的 `additionalProperties`：键 `é` 的值原样进入脱敏投影并参与 `input_hash`，验证器照常放行；
- 非敏感模式 `^\d+$` 配敏感的 `additionalProperties`：键 `١٢٣` 同样泄漏。

仓库内现有契约都没有用 `patternProperties`。缺陷由 S1-AUD-001 引入，本任务建立在 S1-AUD-005 的编译实例缓存之上。

## 验收

- [x] 动态键模式只接受各方言语义相同的子集：规范 §6.4 建议的记号，加 `.`、`(?:…)`、`\d \D \w \W \s \S` 与简单转义。翻译成 ECMA-262 语义的 .NET 表达式后仍用 NonBacktracking 与有界超时；其余构造返回 `AUDIT_SCHEMA_INVALID`
- [x] 键名含方言判断不同的字符（行终止符、非 ASCII 空白、U+0130、代理项），且对象声明了 `patternProperties` 时，该键的值整体遮盖
- [x] UT：上述两个方向的泄漏用例改为遮盖；在方言一致的键名上，翻译结果与验证器方言（.NET ECMAScript 模式）逐例一致，并与独立 ECMA-262 实现（V8）测得的字符集一致
- [x] UT：不支持的构造（词边界、内联选项、Unicode 属性、命名组、类减法、空类、孤立括号、代理项等）在构造策略时拒绝
- [x] `dotnet build Qian.slnx -c Release` 与 `Qian.Audit.Tests` 全部通过；README 写明方言、接受的语法与歧义键的处理
