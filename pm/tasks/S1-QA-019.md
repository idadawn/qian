## 背景

S1-QA-017（PR #265）把 `CustomerCommandTests` 拆成八个主题类并行。在 #262 的分片流水线上（CI 运行 40051232742），Config 132.5 秒达标，`Qian.Sample.Crm.Tests` 178.9 秒未达标：

- 分片 b（Sample.Crm、Events、Files、Registry）整体受 CPU 限制。
  - 同一套分片下 CRM 串行（#262 的运行 40043749259）是 185.9 秒，改为并行后只快了 7 秒。
  - 同一条用例的耗时中位数变为串行时的 5.7 倍；同分片另外三个模块慢到原来的 1.3–2.1 倍。
- 本机直接运行测试程序，89 条：串行 137 CPU 秒、8 线程 139 CPU 秒。CPU 是用例本身花的，不是并行的额外开销。
- 串行时用 dotnet-stack 抽样正在占 CPU 的线程，大头在产品代码：
  - Npgsql 收发约 30%，其中 Kun `TenantRlsConnectionInterceptor` 关连接时的重置约 17%；
  - `PluginLoader` 对账约 11%；
  - 每个宿主现编译表达式树：最小 API 的 `RequestDelegateFactory` 与 EF 查询编译各约 8%；
  - JsonSchema 求值约 5%；测试侧 `Start()` 自身约一成。
- 测试作业的总时长由分片 a 的 `Qian.Scheduler.Tests` 决定（245 秒，105 秒才开跑），CRM 现在不在关键路径上。

可选做法：

- 调分片：CRM 独占一个分片，或按主题类拆到两个分片（要按类筛选）。改的是 `scripts/dotnet_ci.py` 与工作流。
- 压低产品起宿主与访问数据库的 CPU。这同样影响生产，动产品代码前先评估影响面。

## 验收

- [ ] 以 CI 的 TRX 为准，`Qian.Sample.Crm.Tests` 壁钟在 150 秒以内；用例数不少，断言不削弱。
- [ ] 测试作业的总时长不变长（现由分片 a 决定）。
- [ ] 动产品代码时说明对生产的影响，并单独验证。
