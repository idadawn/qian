## 背景

S1-QA-017（PR #265）把 `CustomerCommandTests` 拆成八个主题类并行。在 #262 的分片流水线上（CI 运行 40051232742），Config 132.5 秒达标，`Qian.Sample.Crm.Tests` 178.9 秒未达标（PR 最终头 fb5d53f758 的运行 40056018354 曾 115.1 秒，但合入后不稳定：10 次 110.7–196.8 秒、中位数 158.2、5 次 ≤150，最新 main 40115982759 为 183.6 秒；数据与口径经 S1-QA-017 验收复核更正，R133 ②）：

- 分片 b（Sample.Crm、Events、Files、Registry）整体存在资源争用（模块累计秒 / 首尾跨度秒并行时 2.7–2.9，串行时 1.9–2.0）；CI 侧没有 CPU / iowait 测量，分不出是 CPU、磁盘 I/O 还是 Docker。
  - 同一套分片下 CRM 串行（#262 的运行 40043749259）是 185.9 秒，改为并行后那一次是 178.9 秒；按多次运行比，串行 8 次 185.9–244.4 秒（中位数 214.8），并行 10 次 110.7–196.8 秒（中位数 158.2），中位数快约 57 秒（约 26%）。
  - 并行时单条用例耗时总和是串行时的 5.7 倍（逐条比值的中位数 5.0）；同分片另外三个模块慢到原来的 1.3–2.1 倍。
- 本机直接运行测试程序，89 条：串行 137 CPU 秒、8 线程 139 CPU 秒。CPU 是用例本身花的，不是并行的额外开销。
- 串行时用 dotnet-stack 抽样正在占 CPU 的线程，大头在产品代码：
  - Npgsql 收发约 30%，其中 Kun `TenantRlsConnectionInterceptor` 关连接时的重置约 17%；
  - `PluginLoader` 对账约 11%；
  - 每个宿主现编译表达式树：最小 API 的 `RequestDelegateFactory` 与 EF 查询编译各约 8%；
  - JsonSchema 求值约 5%；测试侧 `Start()` 自身约一成。
- 测试作业的总时长由分片 a 的 `Qian.Scheduler.Tests` 决定（245 秒，105 秒才开跑），CRM 现在不在关键路径上。
- 每次运行都是 `TenantOperationsTests` 最后结束：最后 7.7–14.2 秒只剩它一个类在跑，同分片邻居模块早已结束，这段尾部与 CPU 无关；「tests/ 里压不到 150 秒」未被证实。MaxThreads = 8 而程序集 12 个类，`ShellSurfaceTests` 要等槽位（不在最慢路径，对壁钟无影响）。

可选做法：

- 调分片：CRM 独占一个分片，或按主题类拆到两个分片（要按类筛选）。改的是 `scripts/dotnet_ci.py` 与工作流。
- 压低产品起宿主与访问数据库的 CPU。这同样影响生产，动产品代码前先评估影响面。
- 重新平衡主题类：拆分或挪走 `TenantOperationsTests` 的部分用例，缩短尾部。
- 先测量：分片 b 加 vmstat / mpstat / docker stats 之类的 CPU 与 iowait 采样，证实或否定「受 CPU 限制」；本机的 CPU 秒与 dotnet-stack 占比只统计测试进程、不含 PG 容器，且未附原始数据。

## 验收

- [ ] 测试作业的总时长不变长（现由分片 a 决定）。
