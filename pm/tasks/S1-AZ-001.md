## 背景

与 7.4 互为前置、契约先行：Definition 暴露 `ctx.Authz` 并再导出 `Kun.Authorization` 端口（`IPermissionChecker` / `IDataPermissionFilter` / `IFieldPolicy`；端口归属见 ADR-019 §7 待确认）；`PermissionDefinition`（资源类型、动作、风险级别、step-up、终端）；权限点命名规范 `<plugin-id>:<resource>:<action>`（R9）；`Check / BatchCheck / ListAllowedActions / ListPermissions / Explain` 接口形状；结构化错误码目录（`AUTHZ_DENIED`、`CONSTRAINT_MUTEX`、`CARDINALITY_USER_LIMIT`、`PARTIAL_SUCCESS` …）与多语言文案 JSON 导出。

Kun 2026.10.9 行为变更（S1-KUN-009，2026-10-10）：`Kun.Authorization` 已作为独立包发布，只放端口（`IPermissionChecker` / `IDataPermissionFilter` / `IFieldPolicy`、`AuthorizationSubject`、可解释判定），不内置 RBAC/ABAC，三个入口缺少引擎时一律拒绝且在 handler 前判定——HTTP 用 `services.AddKunAuthorization()` + 端点 `.RequireKunPermission("<权限点>")`，gRPC 用 `[RequiresPermission]`（`AddKunGrpc()` 自动装配拦截器），Mediator 的 `PermissionBehavior` 只有逐命令的泛型注册 `AddPermissionBehavior<TRequest, TResponse>(denied)`（命令须实现 `IPermissionProtectedRequest` 静态声明 `RequiredPermissions`），Kun 没有开放泛型的全局注册；本任务要决定由 `qian.authz` 逐命令注册还是自建全局行为，并用门禁保证受保护命令不漏注册。权限集合不从令牌直接推导。

## 验收
