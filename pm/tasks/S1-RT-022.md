## 背景

S1-CFG-009 差分时发现：配置补丁里的字符串或键名含残缺代理项的转义（反斜杠 u 后接未成对的 D800 至 DFFF 码元）时，.NET 的 SurfaceReader 与 CLI 的 parseSurface 处理不同。YAML：YamlDotNet 报「YAML 语法无效或存在重复键。」，TS 的 yaml 包照常解析。JSON：.NET 读键名时 Utf8JsonReader.GetString 抛 InvalidOperationException，SurfaceReader.Parse 不捕获，profile 装配按无法解析处理；字符串值要到之后取用时才失败；TS 一律接受。S1-CFG-009 只让 profile 装配在配置验证前两端都按无法解析处理，报告的位置与时机仍不同（见 packages/Qian.Profiles/README.md 的已知分歧）。应在表面解析层统一：两端解析时都拒绝含残缺代理项的字符串与键名，给出同一诊断，补表面 TCK 场景。

实施时又确认：

- YamlDotNet 只拒绝未成对的代理项转义，转义的代理对（含高代理用 `\u`、低代理用 `\U` 的写法）照常解码。拒绝时 SyntaxErrorException 指向双引号标量开始的位置，与其他语法错误一样，按扫描顺序先到先报。
- 连续两个高代理项转义时，YamlDotNet 18.1.0 的扫描器调用 Char.ConvertToUtf32 抛 ArgumentOutOfRangeException（上游缺陷）。未闭合的流式集合（如 `a: [` 后换行）抛 InvalidOperationException，SurfaceReader.Parse 原本不捕获，装配与校验直接崩溃。
- 先记下重复键、再遇到致命错误时，.NET 两条都报，CLI 只报致命错误。YAML 里 alias 与重复键同时出现时，两端先报的不同。
- 直接传入的字符串（不经文件解码）可含字面量的未成对代理项：.NET 的 JSON 路径把它们静默换成 U+FFFD，YamlDotNet 与 CLI 原样接受。
- 与代理项无关的其余诊断分歧（YAML 语法错误行号、多文档、JSON 嵌套深度与非有限数值）另建 S1-RT-025。

## 验收

- [x] 两端表面解析器对含残缺代理项的字符串与键名给出同一诊断（JSON、YAML 与 Markdown front matter）：JSON 在所在行报专门文案，语法错误、过深与非有限数值优先；YAML 按语法错误报在标量开始的行，与语法错误、alias 按扫描顺序先到先报，重复键在其后；转义的代理对照常接受；字面量的未成对代理项按值无效处理
