## 背景

S1-RT-021 补求值异常日志时发现：调用方能用超大的数让通用执行入口返回 500。本任务按产品负责人要求（2026-10-15「Reject out-of-range JSON numbers in capability input as 400」）把它改为 400。探针（JsonSchema.Net 9.4）表明边界是 decimal 而不是 double：库比较 `enum`、`const` 与 `uniqueItems` 的取值时调用 `JsonElement.GetDecimal()`，绝对值超过 `decimal.MaxValue`（约 7.9e28）的数会抛 `FormatException`。`[1e28,2e28]` 正常，`[1e29,2e29]`、`1.7e308` 与 `1e400` 都抛；`maximum` / `minimum` 等比较照常工作，下溢的 `1e-400` 按 0 比较、不抛。输入里的这类数（如 `uniqueItems` 的 `[1e29,2e29]`、`enum: [1, 2]` 收到 `1e29`）由调用方触发；输入 Schema 的 `enum` / `const` 里出现这类数（含嵌套在对象、数组取值里的）时，任何数值输入都会触发。S1-RT-021 记录里「超出 double 范围」的说法据此更正为 decimal 范围。

## 验收

- [ ] 输入检查：请求体任何位置的 JSON 数不能表示为 decimal（`JsonElement.TryGetDecimal` 为假）时，在求值前返回 400 `BAD_REQUEST`，与重复成员、孤立代理项同一处理，不执行、不写回执；`decimal.MaxValue` 本身与下溢的 `1e-400` 照常进入校验。单测覆盖 `uniqueItems` / `enum` / `const` 三种原先 500 的情形与边界值；CRM IT 经真实 HTTP 断言 ErrorDetail 为 `BAD_REQUEST`、能力不执行
- [ ] 登记期检查：输入 Schema 的 `enum` / `const` 取值（含嵌套对象与数组）里有不能表示为 decimal 的数时，登记阶段以新规则 `unsupported-number` 拒绝，位置指向该数；单测覆盖顶层、嵌套与边界值，以及经 `CapabilityContractCheck` 的位置映射
- [ ] 求值异常日志：S1-RT-021 的日志用例原靠 `uniqueItems` 比较 `1e400` 触发，本任务后这类输入在求值前即被拒；改为经内部求值入口注入异常，仍断言错误日志带组件 ID 与能力名、异常包装后交给 ErrorDetail 中间件
- [ ] 文档：`packages/Qian.Capabilities/README.md`（执行入口第 2 步、登记期规则表）、组件规格 §9.5、`website/docs/sdk/dotnet/capabilities.md`、SDK `CapabilityContractException` 规则列表与 `docs/CHANGELOG.md` 同步；`check_docs.py` 与文档站构建通过
