## 背景

S1-EVT-002 验收复核（2026-10-23，done）留下的非阻断项。五条验收都成立（验收 5 按 R122），但 Qian.Tenancy 的契约文字仍与消费端实现冲突，几条失败路径没有信号或上界，部分用例没有区分度。

## 验收

- [x] 文档按 R122 对齐：`ITenantContextPropagator.BeginScope` 的注释与 `packages/Qian.Tenancy/README.md` 写明事件消费端的例外与信任根；平台级事件「走独立通道」与实际派发方式（订阅显式 `acceptPlatformEvents` 时在同一队列派发、不开租户作用域）对齐，改文档或改实现择一并写明理由；`packages/Qian.Events/README.md` 与 `QianEventSubscriber.EnterTenant` 的注释改指 R122；定下各 profile 宿主是否登记 `ITenantContextPropagator` 并写进 README
- [x] UT：经传播器进入作用域后核对当前租户等于信封租户，不等即按 `tenant_rejected` 进死信（换成不建作用域的传播器时用例失败）
- [x] 失败路径的信号与上界：`TryMarkProcessedAsync` 返回 false（并发重复，handler 已执行两次）时记日志或计数；死信转发持续失败时原消息反复放回、handler 反复执行，核实 quorum 队列的放回是否计入 `x-delivery-limit`，不计则在消费端加上界；`IsDeterministic` 把全部 `InvalidOperationException`（含 `ObjectDisposedException`）与 `NotSupportedException` 判为确定性失败，收窄或写明口径
- [x] 用例区分度（R112）：CRM「消费端handler内租户为事件租户…」里 `Assert.Contains("tenant_id", Sql)` 恒真（投影本就选了该列），换成能区分 EF 全局过滤的断言；幂等键断言改为等键写入后再查（与 S1-RT-035 修过的同类观测竞态）；「传播器恰好进入 6 次」在瞬时重试下会误报；SubscriberTests 的固定等待改为条件等待；若保留「两个租户并发」，让两个租户的事件在消费侧真正重叠

      - 实现：
        - 转发失败时原地按 `RetryBaseDelay × 2^(n-1)` 退避重发，不放回原消息；

        - 停机仍放回；
        - 结果计数统一改在确认或 nack 之后，rejected 原先在转发之前计。

        - `QianEventsException` 仍为确定性失败；
        - 其他子类（如 `ObjectDisposedException`）按瞬时失败处理；
