## 背景

不可变发布事件（40 位 SHA、CalVer、`dry_run`）→ 验签 → 固定检出 → 构建推送 → 迁移 Job 先行（`--migrate-only`，advisory lock）→ `kustomize edit set image` 按 digest 写回 → Argo 收敛 → smoke（`/readyz` + 参考应用登录）；Argo Application `qian-platform`（L2）、`qian-integrations`（租户接线）；`prune: false` 起步；`Qian.Runtime` 与 profile 随 CalVer 发布。

## 验收

- [ ] 发布前契约门（R114 / S1-DEC-025）：首次发布 qian.tenancy 前确认 TEN-008/TEN-011 已一次收口全部服务端校验约束，发布快照与真实端点一致且边界拒绝测试通过；核对当前平台契约仓库不存在旧基线。若 publish / 发布链已跑过或已有基线，任何 v1 收窄走 v2 与 R33 别名、Deprecation、successor-version Link，不能覆盖旧基线。

- [ ] E2E：从一次发布事件到 staging 三个 profile 镜像全部 `Ready`、外壳经 `gateway` 可访问、参考应用可登录，中间无人工步骤
- [ ] E2E：真实 `qian-platform` 在 staging 经实际协议与认证访问本环境 PG / Redis / RabbitMQ / Apollo，精确网络放行与应用就绪状态一致；记录工作负载镜像 digest、环境端点和脱敏结果。这是发布必过门，不能以诊断 Pod、同名标签、共享服务或仅 TCP 连通代替（DEC-016）
- [ ] E2E：kill `qian-platform` 一个副本，`/readyz` 摘流、无 5xx 泄漏到网关；滚动升级时迁移 Job 先完成再切镜像
- [ ] 检查：Argo `qian-platform`、`qian-integrations` Application 存在且按 digest 引用
- [ ] 迁移装配：生产 `qian-platform` 宿主以 `AddQianData<CapabilitiesDbContext>` 把能力上下文纳入迁移目录并调用 `AddQianCapabilities()`，迁移 Job（`--migrate-only`）经 `IDataMigrator` 执行包内迁移、RLS 由 Qian 迁移生成器补出；staging 真实 PostgreSQL 断言 `__EFMigrationsHistory` 与 `pg_policies`（S1-RT-014 验收 6 的生产侧，R94；测试宿主的同类断言见 `tests/Qian.Sample.Crm.Tests/ProfileEquivalenceTckTests.cs`）
- [ ] 平台授权登录（R103）：生产 `qian-platform` 为 qian.authz 创建专用平台授权登录，迁移 Job 执行 `AuthzPlatformAccess.CreateMigrationSql`，宿主绑定 `PlatformAuthzDbContext`，base 组合包配置 `platformRole`；与审计平台链（`AuditPlatformAccess`）同构，staging 断言平台超管旁路可用、未配置时一律拒绝
