#2. 设计原则

Markdown 链接

状态：已定稿（组件模型 v2，2026-10-07） · 更新日期：2026-10-07 · 决策引用：ADR-002、ADR-003、ADR-005、ADR-006、ADR-009、ADR-011、ADR-016、ADR-018、ADR-019、ADR-020（Accepted） · 上级索引：README

本章把 Qian 的设计原则写成可检验的条目。每条给出 定义、关键区分 / 澄清 与 铁律；铁律是不可违背的约束，违反即为缺陷而非权衡。原则分四组：插件思维（2.1–2.7；2.7a–2.7b 为组件模型 v2 新增，ADR-020）、Agent 就绪（2.8–2.13）、安全硬线（2.14–2.19）、工程原则（2.20–2.22）。功能性细节不在本章展开，见 §07–§10。

#第一组 · 插件思维

#2.1 内核最小集

ADR-020 修订：v2 没有特权内核，本条的「内核」收缩为极小的 Qian.Runtime，注册表 / 生命周期控制器 / 能力目录改为普通插件；见 2.7a。本条原文保留作为「哪些点必须经过、不允许被绕开」的判据。

定义。 内核只保留三类东西：契约（扩展点、能力描述、事件信封、清单 Schema）、强制执行点（租户上下文解析、主体身份与 S2S、权限判定点 PDP/PEP、审计、计量）、注册表（插件注册表与生命周期控制器、能力目录、租户目录）。其余一律是插件（ADR-003）。

关键区分。 「内核」是一个逻辑边界，不等于一个进程：S1 的 qian-platform 既是内核宿主，也承载 module 型系统插件。判断一件事是否属于内核只看一个问题——它是不是每个插件都必须经过、且不允许被替换的点。

铁律。

  • 内核最小集的清单写在 ADR-003 中并闭合；新增内核项必须走 ADR，不得在代码里「顺手」加。
  • 内核不包含任何业务语义（表单、流程、报表、通知渠道等），这些只能以插件出现。

#2.2 系统能力也是插件

ADR-020 / R30：规范术语改为「平台插件」（policy.tier: system，platform profile base 组合包成员），「系统插件」保留为别名；本条原文中的「系统插件」按此读。

定义。 平台自带的租户、身份、鉴权、数据、文件、配置、网关、事件、审计、可观测、外壳、授权、模型网关等能力，按同一份清单以 tier: system 交付，走同一生命周期、同一 TCK（ADR-002）。

关键区分。 tier: system 表示信任等级与不可卸载性，不表示「走后门」。系统插件与第三方插件在声明权限点、注册路由、暴露能力的方式上完全一致；区别只在于允许的 kind 更多（可为进程内 module）且租户不可停用。

铁律。

  • 任何官方能力必须有 qian-plugin.yaml，必须通过 TCK，否则不得进入发布制品。
  • 不允许存在「只有系统插件能用」的内核私有 API；若需要，先把它变成扩展点。

#2.3 清单先于代码，且从代码派生

ADR-020 修订：清单只有一份（.qian-plugin/plugin.json，文件名待 ADR-020 §7 拍板），代码部分的字段由源生成器派生后合并进这一份；声明式表面本身不派生。见 2.7b。

定义。 清单（qian-plugin.yaml）是插件的唯一对外描述：身份、版本、兼容范围、能力、权限点、反向权限、事件、资源、UI 插槽。清单由源生成器从代码派生、CI 校验一致，宿主不执行插件代码即可静态索引（ADR-002）。

关键区分。 「先于代码」指契约评审先于实现；「从代码派生」指清单不允许手写与代码漂移。两者不矛盾：开发者先写契约（接口与特性标注），生成器产出清单，评审清单，再写实现。

铁律。

  • 清单与代码不一致时 CI 失败；手工编辑的清单一律视为无效。
  • 宿主生成路由、权限点、菜单、配置命名空间、OpenAPI 聚合、MCP 工具描述时只读清单，不加载插件程序集。

#2.4 信任等级决定形态

定义。 五级信任 system / official / partner / private / community 决定插件允许的 kind 与 UI 沙箱策略：第三方代码永不进共享进程；partner / private / community 只允许 package / function / connector / 受限 ui（ADR-002；S3 是否允许第三方 service 上架已裁决为「不允许」）。

关键区分。 形态由信任等级决定，而不是由开发者选择。一个 community 插件即使技术上写成 module，平台也拒绝装载。

铁律。

  • 共享进程内只有 system / official 的 module；任何租户可见的第三方逻辑都在进程外或沙箱内。
  • 未签名的插件直接安装失败，不存在「警告后继续」。

#2.5 两层生命周期

ADR-020 修订：平台级生命周期保留；租户级「开没开」改由租户 scope 的 patch 表达，授权状态机只管「买没买」。见 2.7a 与 §03 3.11。

定义。 平台级生命周期（制品 → 修订 → 激活，保留旧修订可回切；状态 Draft → Submitted → Verified → Published → Installed → Active → Deprecated → Retired）与租户级生命周期（授权 → 开通 → 启用 → 升级 → 卸载 → 清除；状态 Available → Entitled → Provisioning → Enabled ⇄ Disabled → Upgrading / Uninstalled → Purged）分开建模（ADR-002）。

关键区分。 平台级回答「这个制品的哪个修订在集群里活着」；租户级回答「这个租户买没买、开没开、用没用」。「Entitled（授权库）」与「Enabled（开关）」分开存储，不得合并为一个布尔值。

铁律。

  • 租户级钩子（开通、升级、卸载）逐租户执行、幂等、可重试，失败不得让其他租户处于半升级态。
  • 「未启用」必须在网关路由、SDK 入口、前端外壳三处同时拦截。

#2.6 一份契约，多处生成

定义。 能力契约（命令 / 查询 / 事件 / 实体，JSON Schema 2020-12）是单一事实源，由它生成 OpenAPI 3.1、MCP 工具描述、权限点、默认工具策略、SDK 客户端与 yue 表单 Schema（ADR-002、ADR-016）。

关键区分。 「生成」不是「同步」：下游产物不允许手工维护再反向合并。契约版本与 schemaSha256 一起进入授权记录，Schema 变即旧授权失效。

铁律。

  • 任一写接口必须能导出完整 Schema；无 Schema 的写入在 CI 失败。
  • 控件注册表、yue 组件 props 的 JSON Schema、设计器、远程渲染白名单与 Agent 生成 UI 共用一份契约，不得各存一份。

#2.7 制品不可变，按 digest 引用

定义。 镜像与插件包（OCI artifact）一经发布不可修改；所有引用使用 @sha256: digest，版本标签只是别名（ADR-002、ADR-017）。

关键区分。 SemVer 服务于兼容性判断，digest 服务于「部署的到底是什么」。两者都要有，但只有 digest 进入发布事件与审计。

铁律。

  • 清单中的 OCI 引用只接受 digest；接受标签引用的安装器视为缺陷。
  • 发布事件按 digest 写回 GitOps 仓库，回切即切回旧 digest。

#2.7a 一切皆插件，没有特权内核

定义。 Qian 的运行时只剩一个极小的 Qian.Runtime（.NET）/ @qian/runtime（TypeScript）：上下文 ctx、服务注册、类型化事件、可逆副作用、加载器。租户、身份、鉴权、文件、配置、网关、事件、审计、低代码运行时、Agent 门面，以及原「内核」承担的注册表、生命周期控制器、能力目录、契约仓库，全部是插件：向共享上下文贡献服务（ctx.<key>）、事件与可撤销的注册。运行中的 Qian 是一棵由 profile、组合包与 patch 层叠出的插件树（ADR-020 D20.1、D20.7）。

关键区分。 2.1 的「内核最小集」在 v2 里收缩为 Qian.Runtime：它没有业务语义，也不包含租户、身份、鉴权的实现——这些是 platform profile 的 base 组合包里的插件，可被替换、被 scope 遮蔽、被 restrict 收窄。「每个插件都必须经过、不允许被绕开」的点（租户、鉴权、审计）不再由内核代码保证，而由 base 组合包里的 waterfall 监听器保证；它们本身也是插件，只是 profile 不允许把它们 patch 掉。能力按 seam 三角色（Service Definition / Provider / Consumer）拆分，换 Provider 不动 Consumer（ADR-020 D20.4）。

铁律。

  • 扩展 Qian 的方式只有一种：把插件挂到其他插件旁边；不存在需要打补丁才能改的特权层。
  • 插件的最小接口是 Inject + Apply；所有注册经 ctx.Effect() 返回释放函数，卸载、重载与 teardown 时逆序撤销。
  • 扩展插件只依赖 Service Definition（Qian.<X>.Abstractions），绝不依赖具体 Provider；组件库唯一必需的 Qian 依赖是 Qian.Runtime（ADR-019 经 ADR-020 修订）。
  • 任一注册要么全局、要么归属恰好一个 scope；scope 不继承（ADR-020 D20.5）。

#2.7b 声明式优先：组件先是文件夹里的清单与表面，代码是可选部分

定义。 组件 = 文件夹 + 清单（.qian-plugin/plugin.json）+ 声明式表面 + 可选代码。表面是 Markdown 与 JSON：skills/、agents/、commands/、hooks/、.mcp.json、tools/、ui/、forms/ lists/ flows/ pages/（S2）、schemas/、config/qian.patch.yml；只有 src/ 是可选的 .NET / TypeScript 代码，发为 NuGet / npm（ADR-020 D20.6）。无代码的组件（只有 skill、只有配置）是常态而非例外。

关键区分。 2.3「清单先于代码且从代码派生」仍成立，但派生的只是代码部分的字段，且只合并进这一份 plugin.json，不再有手写 YAML 与派生文件并存；原 kind 七值退为 runtime.form 的实现细节，顶层分类改为「表面」。声明式表面 S1 支持运行中重载；代码插件的热装卸 S1 不承诺（ADR-020 D20.7）。设计器的保存产物（S2）与 Agent 生成的草稿（S4）天然就是组件文件夹，进 git、进市场、被 patch。安装入口是 qian add <component>，不是 DI 扩展方法或 Helm values（ADR-020 D20.8）。

铁律。

  • 一个组件只有一份清单；清单与表面可被不执行任何代码的工具完整解析、校验与索引。
  • 能用声明式表面表达的，不写代码；代码只承担表面无法表达的运行时行为。
  • 模型可见的一切（tool、skill、提示词片段）都注册在 ctx.Tools 等注册表里并受 scope 过滤；不存在绕过注册表的「隐藏表面」（ADR-020 D20.9）。
  • 文档（配置目录、模块图、事件图、seam 图）由代码与清单生成并设 CI 新鲜度门禁；手写副本视为漂移。

#第二组 · Agent 就绪

#2.8 能力契约机器可读

定义。 每个可调用能力都有名称、意图式描述、输入 / 输出 Schema、副作用等级（sideEffect: read | write | external | destructive）、策略提示、所需 scope、错误码与示例；能力目录按租户与调用者权限过滤，结果带缓存元数据（ADR-016）。

关键区分。 能力目录不等于公开 OpenAPI。生产环境不开放未经鉴权的 OpenAPI 文档；Agent 与开发者看到的都是「经鉴权、按权限过滤」的目录。

铁律。

  • capabilities 条目是 Agent 可发现的最小单元；没有副作用等级的能力不得注册。
  • 工具描述由清单机械生成，暴露范围经策划（agent.expose），不默认全量暴露。

#2.9 元数据即上下文

定义。 应用、数据模型、表单、列表、流程定义本身就是 Agent 理解业务的最佳上下文：以结构化文档存储、带 Schema、带业务语义描述与字段敏感度标签，可经只读资源暴露（ADR-011）。

关键区分。 「给 Agent 的描述」不是另写一份文档，而是元数据自身的字段（标题、说明、语义标签）。为人写的说明与为 Agent 写的说明是同一份。

铁律。

  • 新建一个实体后，能力目录自动出现其增删改查能力；不存在「元数据存在但能力目录不知道」的状态。
  • 字段敏感度（个人信息 / 财务 / 机密）是元数据的一部分，查询与导出必须据此脱敏。

#2.10 人与 Agent 共用权限与审计

定义。 主体模型统一为 user / service / agent 三类，令牌同时表达「谁在执行（actor）」与「代表谁（subject）」的委托链；一个权限引擎服务 UI、API、MCP 三入口；Agent 有效权限 = 委托人权限 ∩ 授予 scope（ADR-006、ADR-009、ADR-016）。

关键区分。 不为 Agent 另造一套平行权限。Agent 不是「超级用户」也不是「匿名调用者」，它永远代表某个人或某个服务主体，并只能做该主体能做之事的子集。签名类动作标 humanOnly；转审、协办、撤销等在 S4 前对 Agent 禁止。

铁律。

  • 审计条目必须含完整主体链（actor、on_behalf_of）、能力 ID、契约版本、输入摘要、来源通道（UI / API / MCP / A2A）。
  • 权限判定返回可解释结果（允许 / 拒绝、原因、命中策略），拒绝原因结构化。

#2.11 元数据变更可校验、可回滚

定义。 元数据采用草稿 / 发布双版本 + 不可变快照；变更以 patch / diff 表达，经 JSON Schema 与语义校验（引用完整性、权限一致性）后才能发布；任意版本可回滚；记录变更来源（谁、哪个 Agent、哪次会话、generatedBy / promptHash）（ADR-011）。

关键区分。 校验是发布前的强制门禁，而不是「用户可选的保存点」。Agent 生成的元数据与人工编辑的元数据走同一条校验链。

铁律。

  • 校验失败必须返回带字段定位的结构化错误，足以让调用方（含 Agent）自行修正。
  • 运行时只读当前生效版本；草稿永远不会被运行时读到。

#2.12 长任务与人在回路资源化

定义。 文件导入导出、批量迁移、审批待办、Agent 补参确认等统一为 Operation/Task 资源，状态机 working / input_required / completed / failed / cancelled，对齐 MCP Tasks 与 A2A Task（ADR-012、ADR-016）。

关键区分。 流程引擎的「待办」与 Agent 的「中断等待输入」是同一个模型的两种触发来源，不允许各建一套。

铁律。

  • 任何预期执行超过一次请求往返的操作必须返回 Operation 句柄，而非阻塞等待。
  • input_required 必须携带结构化输入请求（JSON Schema），而不是自由文本提示。

#2.13 无状态端点 + 可观测计量

定义。 所有对外 API（含未来的 MCP / A2A 端点）不依赖会话亲和，跨调用状态以绑定主体的句柄存储；W3C trace 上下文贯穿网关、服务、事件总线；计量事件带 tenant / app / plugin / principal-kind / model 标签（ADR-010、ADR-016）。

关键区分。 「持有句柄不等于有权限」：句柄必须绑定已认证主体，使用时重新判定。

铁律。

  • 写类能力必须幂等（带幂等键），因为无状态协议下断流重发是常态。
  • 每条请求在追踪系统中完整可见并带租户与主体类型标签；没有 trace 的服务不得上线。

#第三组 · 安全硬线

#2.14 租户只来自令牌

定义。 租户上下文唯一来源是已校验令牌中的 tenant_id claim；生产环境禁用请求头兜底与「默认租户」回退，解析失败即拒绝（fail-closed）（ADR-004、ADR-005）。

关键区分。 后台链路（消息消费、Saga、Outbox 发布、调度回调）同样必须恢复租户上下文；「只有 HTTP 请求有租户」是 Kun 当前的缺口，S1 必修（ADR-001）。

铁律。

  • 任何能力的 inputSchema 不得出现租户字段；契约 lint 强制。
  • 跨租户访问没有例外路径；平台超管对租户不可见（审计可见）。

#2.15 权限不进令牌

定义。 令牌只含身份、tenant_id、membership_id、scope、identity_revision（及预留 profile、act）；权限按主体缓存并以 identity_revision 递增即时失效（ADR-006）。

关键区分。 scope 是客户端被授予的能力范围上界，不是用户的权限集合；权限判定永远在服务端完成。

铁律。

  • 权限变更必须即时生效（identity_revision 递增 + 推送刷新），不允许「等令牌过期」。
  • 前端权限裁剪只是体验层，不构成任何安全边界。

#2.16 所有写操作走带 Schema 的命令

定义。 一切写入经命令端点：名称 + 输入 / 输出 Schema + 副作用等级 + 幂等键 + 可选 dryRun；UI、API、MCP 同一入口（ADR-016）。

关键区分。 低代码数据引擎的泛型命令（创建 / 更新 / 删除 / 查询记录）同样遵守此原则，在唯一入口做「资源 + 动作 + 行级」三段式校验，不依赖设计器勾选或客户端传参（ADR-011）。

铁律。

  • 不存在绕过命令层的直写路径（含运维脚本以外的任何服务端代码）。
  • 破坏性能力必须支持 dryRun 与软删除。

#2.17 不用 eval

定义。 服务端与前端都不以 eval / new Function / 进程共享脚本引擎执行租户提供的脚本。公式与规则用可序列化表达式 DSL（JSON AST）解释执行；前端兜底为隔离沙箱（白名单 API、超时、内存上限、不暴露令牌）；服务端自定义代码只落 Wasm function 沙箱（ADR-011、ADR-013）。

关键区分。 「声明式优先」不是能力阉割：三层联动（声明式动作 → 表达式 DSL → 沙箱脚本）覆盖参考平台绝大多数场景；自由 JS 按钮明确不做。

铁律。

  • 表达式引擎只允许函数注册表中的函数，拼接 SQL 判条件视为缺陷。
  • 动态数据引擎 SQL 生成全部参数化 + 标识符白名单。

#2.18 令牌不进 URL

定义。 访问令牌不出现在 URL、查询串、iframe src 中；外链、预览、下载使用一次性票据或 postMessage 握手；前端不持久化令牌与加密密钥（ADR-013）。

关键区分。 「分享链接」「预览票据」由内核签发、服务端校验、带有效期与范围，是能力而不是绕过。

铁律。

  • 匿名可访问的入口必须显式标注 anonymous: true 并经审计。
  • 不允许任何「公有免鉴权」的开放接口形态；对外接口凭据统一为网关的应用级客户端凭据。

#2.19 第三方代码不进共享进程

定义。 第三方（partner / private / community）插件只能以 package（纯元数据）、function（Wasm 沙箱）、connector（受控出网）、受限 ui（Worker 远程渲染或 iframe 沙箱）形态存在；连接器出网经平台出口代理与域名白名单（ADR-002）。

关键区分。 私有化客户在自己的集群里装自己的 service 是运维行为，不改变共享 SaaS 的规则。

铁律。

  • 共享进程内不存在任何第三方可执行代码路径。
  • 第三方插件对平台的「反向权限」（能调用哪些内核能力、能否出网、能否持久存储、需要哪些密钥）在清单中声明，租户管理员开通时逐项批准，升级新增即重批。

#第四组 · 工程原则

#2.20 规范描述目标态，并标注过渡态

定义。 PRD 与 spec 描述预期行为；与当前实现、协议或运行状态有差异时，用带日期的「过渡态」块明确记录，并写明何时删除该说明。

关键区分。 不把设计当成已落地事实，也不把临时妥协写成目标态。S1 接受「预装全部官方 module + 按租户开关」是明确标注的过渡态（ADR-002）。

铁律。

  • 过渡态块必须带日期与退出条件。
  • 决策理由不在 PRD 重复，只引用 ADR 编号。

#2.21 以代码为准

定义。 Kun 的文档与代码不一致时一律以代码为准；Qian 的清单从代码派生；契约从源生成器导出；验收以可运行的测试与真实环境为证据。

关键区分。 「以代码为准」不是「不写文档」，而是文档中凡能从代码生成的部分一律生成，不手写第二份。

铁律。

  • 任何「已完成」判定必须附证据（命令、环境、结果）；合并不等于完成。
  • 没有真库集成测试的隔离策略不得作为默认策略。

#2.22 每阶段独立交付、有退出标准

定义。 S1–S4 每个阶段都有可验收的退出标准（ADR-018、§16），每个阶段的交付物可独立运行、独立售卖或独立被开发者使用，不依赖下一阶段补齐。

关键区分。 「独立交付」不等于「互不相关」：后一阶段只在前一阶段的契约上叠加，不推翻。S1 起就要做对的 Agent 防返工清单是跨阶段约束。

铁律。

  • 退出标准未达成不进入下一阶段的功能开发（允许并行做设计与 PoC）。
  • 任何阶段都不允许「先上线再补多租户 / 鉴权 / 审计」。
