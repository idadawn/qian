## 1.1 一句话定位

> **Qian（乾）是一个以插件思维构建、为 AI Agent 时代准备的多租户低代码 PaaS：运行时 `Qian.Runtime` 只保留上下文、服务注册、类型化事件与可逆副作用，平台自身的每一项能力（含注册表与生命周期）都以插件交付，组件化按 Agent 时代的做法——文件即组件、一键安装、一切皆插件（ADR-020）；开发者先用它写出多租户应用，业务搭建者再在其上搭建表单与流程，租户最终在应用市场自助选购，而 Agent 从第一天起就能通过同一套契约发现、调用并生成这些能力。**

把这句话拆开：

| 成分            | 含义                                                                                                                                                                                                                                     | 真相源                                                             |

## 1.2 与同类的分化

| 维度        | 传统低代码平台                      | Agent 平台                 | **Qian**                                                                                                         |
| --------- | ---------------------------- | ------------------------ | ---------------------------------------------------------------------------------------------------------------- |
| 首要用户与起点   | 业务人员与 IT 支持；一上来就给设计器         | Agent 开发者；一上来就给编排画布与模型接入 | **先给开发者 SDK/CLI/TCK，再给搭建者设计器，再给租户市场；Agent 契约从 S1 起贯穿**                                                           |
| 平台能力的组织方式 | 内置模块，功能按菜单堆叠，系统能力与业务能力两套代码路径 | 工具 / 模型 / 策略等类型化插件       | **极小运行时 + 一切皆插件；平台能力也是插件（平台插件），同一清单、同一运行时语义、同一 TCK；一份清单派生路由、权限点、菜单、配置命名空间、OpenAPI、MCP 工具；文件即组件，`qian add` 一键安装** |
| 多租户       | 事后加租户列，租户解析常有请求头兜底与默认回退      | 多为工作空间级隔离，不承诺数据层隔离       | **租户只来自已校验令牌、fail-closed；共享库 + RLS 双保险；租户级生命周期是一等模型，并提供高隔离与私有化两档**                                               |
| 身份与权限     | 自有账号体系，权限校验分散在控制器，可被客户端参数绕过  | API Key 为主，权限随 Key       | **平台唯一 issuer（OpenIddict）；权限点由插件清单声明；单一判定点服务 UI / API / MCP 三入口；权限不进令牌、决策可解释**                                   |
| 元数据       | 隐式契约，前后端各自理解；改表等于删表重建        | 工作流 JSON，校验弱、回滚靠人        | **带 Schema、版本化、可 diff、可回滚的元数据；正式的 Schema Migrator；元数据本身即 Agent 的上下文**                                            |
| 应用分发与升级   | 模板复制为主，升级靠人工重导，导出包丢菜单与权限     | 面向开发者的插件市场               | **应用 = 组合包 + marketplace 条目（原 bundle，R28）；template / managed 两种分发；组件格式、升级冲突处理、权益 API 在 S1 定型**                   |
| 扩展代码的位置   | 进程内脚本引擎、热插 DLL               | 沙箱或外部进程                  | **第三方代码永不进共享进程；信任等级决定允许的形态；前端不可信 UI 走沙箱**                                                                        |
| Agent 的角色 | 事后加一个「AI 助手」入口               | 平台核心                     | **能力目录就是 Agent 的发现入口；写操作带 Schema 与副作用等级；Agent 作为一等主体、持委托链；S4 对接外部 Agent 运行时而非自建**                                |
| 模型接入      | 直连厂商 API，各模块各自配置             | 自带模型抽象层                  | **复用模型服务网关（GPUStack + Higress）；平台只做租户、配额、计量，不自写模型代理**                                                            |
| 部署与运维     | 单体或多进程单库，配置散落                | 云托管为主，私有化弱               | **K3s + GitOps + Apollo；按 digest 的不可变发布；默认共享、高隔离租户、私有化整套 overlay 三档拓扑**                                          |

## 1.3 为什么现在

1. **行业已把 AI 写进低代码的品类定义。** 调研（`research/notes/d3-web-market.md`）确认：权威分析机构 2026 年新版低代码应用平台象限直接以「AI 增强型」命名，其 2025 年的规划假设认为未来几年大部分企业会经由低代码平台落地 Agent；主流厂商都在做同样三件事——自然语言生成应用元数据、把平台能力以 MCP / CLI / Skills 开放给外部编码 Agent、在市场里上架 Agent 组件。一套 2026 年才开始建的平台若不把这些写进底座，上线即落后。
2. **Agent 协议层刚刚稳定，可以押注。** MCP 已进入中立基金会治理，2026-07-28 版把协议改为无状态、授权对齐 OAuth 2.1 与资源指示器；A2A 1.0 已稳定；官方 C# SDK 与 Higress 均已跟进。以这套标准为目标版本从头设计，比在旧协议上修补便宜得多（`research/notes/d5-web-agent-native.md`）。
3. **「平台托管运行时 + 数据不出平台」成为市场信任标签。** 外部托管的集成框架正在被平台托管形态取代，公有 SaaS 普遍「禁第三方任意代码、允许纯元数据包」。Qian 跑在 K3s 上并以组件（文件夹 + 清单 + 声明式表面，无代码组件是常态）为分发单元，天然适合这一形态。
4. **我们自己的前置条件已经具备。** Kun 已有可生产的核心模块与多租户、Outbox、RLS 等设计；团队已有 K3s / GitOps / Higress / MaaS 基础设施与一套经过验证的 React 工程规范；参考平台的功能全集与反例已完成七个领域的基线梳理（`research/baseline-digest.md`）。缺的是把它们按正确的顺序组装起来。
5. **再晚就要为旧设计买单。** 基线明确列出「S1 起就要做对、否则 S4 返工」的清单（带 Schema 的写命令、统一主体模型、可解释权限、一份契约多处生成、租户只来自令牌、审计含主体链）。这些都是底座层的决定，越早定越便宜。

## 1.4 为什么是插件思维

- **运行时小才守得住。** 多租户、身份、鉴权是平台的可信计算基，必须「不可绕过」；v2 没有特权内核：运行时 `Qian.Runtime` 只剩上下文、服务注册、类型化事件、可逆副作用与装载器，租户、鉴权、审计的强制执行点是 `platform` profile base 组合包里的 waterfall 监听器（profile 标记为不可移除，patch 动不了），一切可替换的东西都是插件，运行时才能小到可以被完整审计与测试（ADR-020 D20.1）。
- **平台能力也是插件（平台插件，原称系统插件），平台才会吃自己的狗粮。** 租户、身份、鉴权、文件、配置这些官方能力按同一份清单、同一运行时语义、同一 TCK 交付，连注册表与生命周期控制器本身也是插件（`qian.registry` / `qian.lifecycle`），意味着第三方插件遇到的每一个坑官方插件会先踩到；SDK 的质量由平台自己先担保。
- **一份清单派生一切，Agent 才有可读的契约。** 清单（`.qian-plugin/plugin.json`；代码部分的字段由源生成器派生并合并进同一份）静态可索引，宿主不执行插件代码就能生成路由、权限点、菜单、配置命名空间、OpenAPI 聚合与 MCP 工具描述。这正是 Agent 就绪所需的「能力契约机器可读」，不是另起一套。
- **组件化按 Agent 时代的做法，而不是传统平台设计。** 文件即组件：组件 = 文件夹 + 清单 + 声明式表面（skill / agent / command / hook / MCP 服务器等 Markdown 与 JSON，Agent 可直接读写）+ 可选代码，无代码组件是常态；一键安装：`qian add <component>` 一条命令装进任何项目，目录市场是 git 仓库里的一份 `marketplace.json`；一切皆插件：没有需要打补丁的特权内核，能力按 seam 三角色拆分，换一个 Provider 就改变整个产品（ADR-020，§03 3.4a）。
- **信任等级决定形态，才能同时服务 SaaS 与私有化。** `policy.tier` 决定允许的 `runtime.form` 与 `policy.sandbox`：官方 `module` 进程内编译期并入；第三方只能是声明式表面、`package` / `function` / 受限 `ui` 以及为某个 seam 提供 Provider 的组件（原 connector，R28），永不进共享进程。同一套模型下，共享 SaaS 可以安全开放生态，私有化客户可以装自己的 `service`。
- **应用市场只是插件机制的延长线。** 应用 = 组合包 + marketplace 条目（R28）；S1 末「一切皆包」跑通——`qian add` 一键安装与 `marketplace.json` 目录市场从 S1 就有，S2 低代码应用可打包（设计器保存即产出组件文件夹），S3 的商业市场（授权、计费、审核）叠在同一格式之上，不另起格式。市场不是另一个子系统，而是同一制品流水线换一个消费者。

反过来说明确不做的事（ADR-002、ADR-020 D20.11）：为第三方代码与可 AOT 的边缘 profile 做运行时热插 DLL（R27）、进程共享的服务端脚本引擎、把 sidecar 作为默认依赖、引入许可证受限的开源低代码 / AI 平台代码；也不再按物理形态做顶层分类、不维护第二套清单格式。

## 1.5 为什么先做开发者底座

- **低代码运行时的每一层都压在底座上。** 动态数据引擎要复用租户上下文、RLS、Outbox；审批引擎要复用组织模型、事件总线、调度、表达式规范；设计器要复用元数据版本化契约。先把这些做成可被代码直接消费的技术组件，S2 的引擎才有地基，否则会像参考平台那样在引擎里重复实现一遍租户与鉴权。
- **开发者是最严格的验收者。** 「开发人员用代码在 Qian 上写出一个多租户应用，登录、鉴权、存储、文件、配置、网关、事件、审计全部由平台提供」是 S1 的退出标准（ADR-018）；ADR-020 §6 又加了一条：在空白项目里 `qian add identity authz files` 后 30 分钟内跑通登录、权限检查与上传，不部署 Qian 平台。能让开发者半天写完一个多租户应用、30 分钟装好通用能力的 SDK，才配承载低代码。
- **底座错误最贵。** Kun 当前在多副本多租户下的关键路径缺口（后台链路丢租户、消息至多一次、Outbox 无锁、网关不强制认证）必须先修并用集成测试实证（ADR-001）；这些问题一旦被低代码应用放大，修复成本是数量级增长。
- **插件机制与 SDK 本身就是第一款产品。** 开发者插件市场（面向开发者的组件与连接器）与 S3 面向租户的应用市场共用同一套组件格式（文件夹 + 清单 + marketplace 条目）与发布流水线，只是消费者和授权模型不同；S1 把组件格式做对，后面两步才不返工。
- **Agent 就绪不能靠事后补。** 统一主体模型、可解释权限判定、带 Schema 的写命令、审计含主体链都是底座层约定，在 S1 落地的成本最低，在 S4 补的成本最高。
