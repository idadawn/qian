> 来源基线：F（应用 / 表单 / 列表 / 视图 / 发布）。相关决策：ADR-002 插件模型、ADR-006 鉴权、ADR-008 事件、ADR-011 元数据与动态数据、ADR-013 前端 yue、ADR-014 市场；PRD §07（S1 模型与契约）、§08（S2 低代码构建）、§12（边界）。
> 口径与优先级标记同映射 01。本域的「S1·P0（契约）/ S2·P0（界面）」写法表示：契约与服务在 S1 落地供代码开发使用，可视化配置界面在 S2 交付。

## 0. 本域的迁移判断

参考平台这条链路（应用 → 功能 → 表单 / 列表设计 → 发布到菜单与权限资源 → 动态数据引擎）的**产品形态**是成熟的，值得整体借鉴：三栏设计器、向导式三步、未发布 / 已发布 / 已修改三态、权限「双重门」、条件构造器五处复用、导入向导五步。但其**实现**有四处必须推翻：元数据没有 Schema（70 种控件共用一个大一统 POCO，前后端各维护一份隐式契约）；业务列没有迁移管道（只补系统列，改表等于删表重建）；动态引擎约 47 处拼 SQL、租户值字面量、客户端参数可绕过鉴权；运行时与代码生成两套实现导致能力漂移。Qian 按 ADR-011 走元数据驱动运行时主轨：元数据版本化、可校验、可 diff、可回滚；动态表「物理主表 + JSON 列」混合存储、不走 EF 模型；统一 Filter AST；正式 Schema Migrator；代码生成退化为 S2 后期可选薄壳。

| 控件类型映射表 + switch               | `FieldType` Catalog 条目（dbType、长度、精度、可索引、多值策略、provider 五方法）                                                                                        | 单一事实源                  |
| 无迁移计划                          | `MigrationPlan`（steps、dataLoss、tenantsAffected、状态）                                                                                                | 可审核、可追溯                |
| 系统表单登记（手填）                     | `CapabilityManifest`（code、kind、routes、api、buttons、fields、flowForm、anonymous、permissionKinds、dependsOn）                                            | 由 SDK 从代码派生            |
| 应用包 `.bs` / 功能包 `.vdd`         | bundle（元数据 + 依赖清单 + id 重映射表 + 权限策略 + 种子数据 + 迁移脚本）                                                                                                 | 市场安装包的同一格式             |

## 3. 明确不做清单

| 不做的能力                            | 原因                                                                        |
| -------------------------------- | ------------------------------------------------------------------------- |
| 参考平台形态的代码生成（完整 CRUD 源码 + 手工接入）   | 制造第二真相源与能力漂移；生成物不发事件、不校验按钮；Q11 已裁决不作主轨                                    |
| 控件 / 按钮 / 表单生命周期的自由 JavaScript   | `eval` 暴露访问令牌、安全面大、对 Agent 不透明、小程序端失效；以声明式规则 + 表达式 DSL + 服务端 Hook 替代（Q18） |
| 匿名外链照搬（读草稿、不校验开关 / 密码 / 条件、无有效期） | 以服务端签发的能力令牌重做                                                             |
| 树形表格「清空数据权限取全量」                  | 任何布局不得跳过数据权限                                                              |
| 全量用户表进缓存 30 分钟                   | 多副本不一致、大租户不可行                                                             |
| 两份端配置（PC / 移动各一份列表配置）            | 一份 schema + `device` 覆盖                                                   |
| 动态表走 EF 模型、每功能一组 `DbSet`         | 与 Kun 编译期世界观冲突；按 ADR-011 走混合存储 + SQL 生成                                   |
| 「改表 = 删表重建、只允许空表」                | Schema Migrator 替代                                                        |
| S2 移动端 H5 表单渲染器                  | Q13：S2 只做 PC 响应式，预留端覆盖；H5 S3 可选                                           |
| 多种专有后缀导出包（`.bs` / `.vdd`）        | 统一元数据包与 bundle 格式                                                         |

## 4. 必须修正的做法

| #  | 参考平台做法                                                 | 风险             | Qian 替代做法                                            |
| -- | ------------------------------------------------------ | -------------- | ---------------------------------------------------- |
| 1  | 约 47 处字符串拼 SQL；逗号连接代替 JOIN；租户值字面量；路由 id 与版本值直接入 SQL    | 注入、跨租户         | 参数化 + 标识符白名单 + 查询构建器；租户与软删谓词强制注入；RLS 兜底              |
| 2  | 鉴权分散在控制器，依赖客户端 `menuId` / `flowIds`；移动端控制器无校验；数据权限只管列表 | 越权读写           | 引擎唯一入口「资源 + 动作 + 行级」三段式（ADR-006）                     |
| 3  | 权限四开关放模板 JSON：关闭即跳过鉴权、未挂菜单即放行                          | 设计者一个勾选决定安全    | 开关只产出可授权项清单；鉴权独立于设计者勾选                               |
| 4  | 元数据无 Schema，70 种控件共用 947 行 POCO，前后端隐式契约                | 不可校验、不可生成、不可迁移 | 版本化 JSON Schema，后端保存校验，前后端共用校验器                      |
| 5  | 只补系统列、无业务列迁移；改表等于删表重建                                  | 生产库不可演进        | 元数据 diff → 迁移计划 → 审核 → 逐租户执行（ADR-011）                |
| 6  | 发布无事务边界，跨主库与业务库写十几张表分开提交                               | 半发布态           | 编译 → 迁移 → 切流 → 挂载的可重放幂等步骤 + Outbox + 发布日志            |
| 7  | 乐观锁先查后改非原子、可被请求键跳过                                     | 并发覆盖           | 原子更新、`version` 比对不可绕过                                |
| 8  | 数据事件事务提交前发布、订阅端吞异常                                     | 丢事件、假成功        | Outbox 至少一次 + 失败可见（ADR-008）                          |
| 9  | 控件三处呈现（编辑 / 只读 / 单元格）各自硬编码；控件 key 分散两处                 | 新增控件改三处        | 注册表一次声明 edit / readonly / cell + Field Type Provider |
| 10 | 导出包不含菜单 / 权限 / 字典 / 表结构，导入不重映射 id                      | 迁移靠人工修复        | bundle 含依赖清单与 id 重映射表（ADR-014）                       |
| 11 | 文件默认路径、OCR 地址写在后端配置文件                                  | 环境耦合           | 进 Apollo；上传策略归 `qian.files`                          |
| 12 | 子表「选择数据」、关联表单等跨表单引用无统一元数据                              | 无法分析影响面        | 表单引用图独立机器可读                                          |

## 5. 未决问题

1. **外链填单 / 公开查询的阶段**：基线 F 为 S3 可选（需能力令牌重做），P 基线附录 B 为 S2 可选；决策清单未裁决。本文件按 S3·P1 写；若 S2 客户演示需要匿名采集表单，需提前到 S2 并同步交付能力令牌。
2. **`qian.expression` 的归属**：K 基线把表达式解释器归入 `qian.forms`，F 基线建议独立 `expression-engine`（S1 可先做），W 基线要求 S1 定规范供流程条件共用。本文件采用独立 `qian.expression`（S1 契约 / S2 实现）并在 README 插件总表标注别名，需确认。
3. **低代码业务库是否允许租户自带连接**：D4 / D11 列为待拍板但 Q 表未给默认；影响 Schema Migrator 的跨库执行与数据权限拼接。本文件按「S1–S2 仅平台库，租户自带连接 S3 评估」写。
4. **多值字段默认存储策略**：ADR-011 允许「原生 JSON 列或关联表」两种，哪一种是默认（影响可索引性与 in / join 查询）尚未指定；建议 Field Type Catalog 逐类型声明，默认 JSON 列、可查询多值用关联表。
5. **控件目录基线口径**：以参考平台前端设计器 59 + OCR 9 为骨架，但 S2 实际交付的控件子集（附录 A 中 S2 必做约 40 个）是否需要进一步收缩以配合 yue 路线 A 的人力风险（Q12 已接受风险但未定收缩清单）。
6. **代码生成薄壳的时点**：Q11 定为「S2 后期可选」，但 S2 后期人力集中在流程域；若 S3 ISV 需要脚手架才能上手，是否顺延到 S3 初。
7. **数据管理页与设计权限的关系**：参考平台「有设计权限即有数据管理权限」；Qian 要求数据管理也走数据权限，开发者在开发态是否需要一个显式的「全量数据调试」权限点，需产品确认。
